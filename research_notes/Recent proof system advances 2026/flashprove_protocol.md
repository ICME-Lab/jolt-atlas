## 1. Field and code: which field, extension, rate, interleaving, queries, proximity regime, hash; encoding of small integers and cost of one committed trace element

### Takeaway
Goldilocks (p = 2^64 − 2^32 + 1) with a cubic extension (X^3 = 2, 192 bits) for every challenge; Reed–Solomon over a 2^32 domain, proximity tested up to just under the Johnson radius with out-of-domain samples, 128-bit per-round target reached only with 20–32 bits of grinding on query rounds; BLAKE2b. Trace integers are signed bytes packed three to a base-field element (radix 2^20), so a committed byte costs one third of a 64-bit message symbol.

### Cited Findings
- **[SRC]** Base field p = 2^64 − 2^32 + 1 ("Goldilocks"), E = F[X]/(X^3 − 2); 2 is a cubic non-residue because 3 divides p − 1 only once; reduction follows plonky2's `reduce128` — `blocks/field/gl64.h:6-33`, `blocks/field/field.h:6-23` ([FP](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/blocks/field/gl64.h)). **[PAPER]** Table 2 agrees: "F, p = 2^64 − 2^32 + 1; E = F[ϑ], ϑ^3 = 2" (paper.txt:704-707). The field choice "takes up a suggestion" of Chiesa–Fenzi–Weissenberg (paper.txt:4912).
- **[SRC]** A scalar sent in a proof is one element of E, 24 bytes — `docs/format/11-1-machinery.md:25` ([FP](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/format/11-1-machinery.md)).
- **[PAPER]** Weight table at the default configuration: domain |D| = 2^32; each row's message ℓ = 402,653,184 entries plus t = 44,040,191 random low coefficients (the zero-knowledge "opening budget"); rate ρ = (ℓ + t)/|D| = 0.1041; 2^v = 2^11 interleaved rows; decoder radius δ = 0.6640; one OOD answer per row; ν_on = 64 columns opened per batch (62 for the offline and link proofs); proof-of-work 20 / 28 / 32 bits (request rounds / shared batch rounds / offline) — paper.txt:704-726 (Table 2). **[SRC]** cross-check: `prover/examples/target_full_f2/policy.txt:2-32` has `sec 128`, `answers 1`, `work positions 20 28 32`, `table 11 32 402653184 44040191 0 18`; `docs/format/08-parameters.md:835-846` gives rate 0.104004, one-time distance 0.664066 "Johnson", list size 26, 64 columns per batch, 62 for the one-time test and link, leaf-table limit 688,127 batches ([FP](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/format/08-parameters.md)).
- **[SRC]** Trace (segment) codes, from the derived table at the full-size parameter lines (`record.f2.txt` column = first 32 lines of `target_full_f2/policy.txt`): group `link`, stage 1 uses base code (length 2^23, ℓ = 4,194,304), δ = 0.290134, list size 54, 219 positions; later stages use lengths 2^22 … 2^13 with δ ≈ 0.75–0.82 and 44–55 positions each. Groups `folded`/`omega`/`own` (the test on the weight table) start at (2^24, ℓ 2^22) δ 0.497, 101 positions, or (2^22, ℓ 2^18) δ 0.747, 51–55 positions — `docs/format/08-parameters.md:780-830`. **[PAPER]** Table 2 names δ_seg = 0.2901 with 219 positions as "proximity parameter of a segment's first proximity test" (paper.txt:718-719); in the format a "link" is a segment (`docs/format/11-2-feed-forward-segment.md:12-13`).
- **[SRC]** All closeness rounds at the full-size file (63 key-file, 23 leaf-file, 255 per proof = 341) rest on the beyond-unique-decoding theorem, none on the unique-decoding bound — `docs/format/08-parameters.md:855-859`; 324 of the 341 reach 128 bits by less than a tenth of a bit, and without proof of work the weakest round has 96.23 bits — `docs/protocol.md:226-232` ([FP](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/protocol.md)).
- **[PAPER]/[LEAN]** The proximity results used are mutual correlated agreement strictly below the Johnson radius: Ben-Sasson–Carmon–Haböck–Kopparty–Saraf (ePrint 2025/2055, Thm 4.6) "taken as given" by the programs, with a two-word case machine-checked in Lean via ArkLib/Mathlib (Lemma 5.13) — `docs/protocol.md:119`, paper.txt:4859-4862.
- **[PAPER]** Proximity test = Batching, then per stage Fold (a masked sumcheck) + Code switch (send the folded row under a shorter code, open the old group at sampled positions), then a Base case; these are Constructions 6.3, 9.7, 7.2 of Chiesa–Fenzi–Weissenberg ePrint 2026/391 (version of 25 Feb 2026) "with changes" — paper.txt:4512-4551. OOD sample after every data-carrying message, masked by a pad × nonzero factor (paper.txt:4528-4529, 791-805).
- **[SRC]/[PAPER]** Hash: BLAKE2b with 32-byte outputs, modelled as a random oracle; a second fixed BLAKE2b variant (counter-tweaked) digests public tables — paper.txt:911-931, 4718-4724; `docs/model.md:154-160`. Merkle leaf = one column (all interleaved rows at a position) plus a salt (`docs/protocol.md:95`).
- **[SRC]** Encoding of small integers: each trace matrix of "cells" (integers; a signed byte for the honest prover) is committed packed: `M[i'][c] = cell(3i', c) + 2^20·cell(3i'+1, c) + 2^40·cell(3i'+2, c)` over F; constants `LANES = 3`, `LRAD = 20` — `docs/format/11-1-machinery.md:1095-1116`. Build-time assertions: 2^20 ≥ 4·2^17 − 1 and (4·2^17 − 2)(1 + 2^20 + 2^40) < p so a packed entry has at most one unpacking into integers in (−2^18, 2^18); four lanes would overflow p — `docs/format/11-1-machinery.md:1463-1470`; same condition in `blocks/iop/rng.h:141-148` ([FP](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/blocks/iop/rng.h)).
- **[SRC]** Multi-byte values are "tensors" with `nl` limbs: value = Σ 256^lb · cell (limbs are signed cells; the decomposition is explicitly not unique and not specified) — `docs/format/11-2-feed-forward-segment.md:396-405`, `:252-254`.
- **[SRC]** Weights: every weight is written in signed base-2^8 digits, two digits per weight (range [−2^12, 2^12)), four for an embedding entry; digits are placed in one d × 2^n digit matrix (d = 3,076,096 matrix rows, n = 18) whose blocks are the 2^11 table rows — paper.txt:766-787 [PAPER]; `docs/protocol.md:113` and `docs/model.md:96-98` [SRC-level docs]; `wb_* 13` lines in `policy.txt:72-83,116`.
- **[LEAN]/[PAPER]** Headline soundness: ε(q) ≈ 16·(q + 2^23)/2^128 ≈ q/2^124 + 2^−101 for the Lean verifier, random-oracle model, exact-match policy; each round ≤ 2^−128 with proof-of-work bits counted — `docs/protocol.md:236`, paper.txt:114-128; README states the same figure.

### Inferences
- **[INFER]** Trace encoding is cheap by rate: a segment's first oracle group is rate 1/2 (2^22 message, 2^23 codeword) tested at δ ≈ 0.29 with 219 queries, i.e. FlashProve spends queries (proof size) to keep the trace NTT at blow-up 2. Only later folded stages and the weight table (rate ≈ 0.104) use low rates. This reading of "(length, ell, r)" as (codeword length, message length, something else) and of group `link` as the per-segment group is mine; the format's 8.4 was not read line by line.
- **[INFER]** Cost of one committed trace byte: 1/3 of a Goldilocks message symbol, so at rate 1/2 about 2/3 of a 64-bit codeword symbol to NTT and hash (≈ 5.3 hashed bytes per byte cell, before the Merkle interior). A 16-bit value (2 limbs) costs 2/3 of a message element. Compare jolt-atlas: 12 one-hot 4-bit digits per matmul output under a lattice commitment.
- **[INFER]** 192-bit challenges over a 64-bit base field give the "small field for data, big field for soundness" split that lets every Schwartz–Zippel-type loss (including grand products over 2^30 keys) stay far below 2^−128 without any instance-size penalty.

- Exact meaning of each number in the `group`/`stages` lines (interleaving count per segment message, mask-code sizes) was not decoded; `docs/format/08-parameters.md` §8.4 defines them.
- No statement of the hash throughput or NTT implementation details beyond file names (`prover/field/transform_groups_gl64.cuh`, `prover/engine/encode_kernels.cuh`); not read.

## 2. The approximate range check: construction, bound proven versus honest bound, completeness error, soundness argument, zero-knowledge, and use with virtual tensors

### Takeaway
It is the Lyubashevsky–Nguyen–Seiler / Gentry–Halevi–Lyubashevsky random-projection check: the verifier draws a k × 128 matrix Θ with entries 0 (prob. 1/2), ±1 (1/4 each), shared by all rows of a trace matrix; the prover commits two digits (10 + 8 bits) of every row-combination Y·Θ and a lookup range-checks those digits. It proves |cell| < 2^18 when honest cells are signed bytes (slack 2^11), with soundness error 2^−128 for the Θ round and an honest failure probability ≤ 2e^−128 per combination. It does not prove any exact range; exact ranges come from 2^16-table lookups on composed keys (section 3).

### Cited Findings
Construction
- **[SRC]** Round `RNG`: after the segment's packed cell arrays and the read vector `U3` are committed and their OOD samples answered, the verifier samples (Σ_μ k_μ) × τ entries in {−1, 0, 1}; `Θ_μ[c][u]` multiplies column c of matrix μ in combination u; "the same entry multiplies every cell row of that column, the packed entries of that column, and the entries of U3 that belong to that column" — `docs/format/11-1-machinery.md:1147-1171`. τ = 128 (`policy.txt:63`); the verifier requires τ ∈ {32..256}, multiple of 32, τ ≥ `sec` (`11-1-machinery.md:1367-1369`).
- **[SRC]** Distribution: 0 with probability 1/2, +1 and −1 with 1/4 each; drawn by `rng_theta()` / `chainTrits()` (C++ verifier) / `draw_matrix()` (CUDA prover) — `blocks/iop/rng.h:332-383`, `verifier/src/vf_transcript_channel.h:93-102`. **[PAPER]** same (paper.txt:4739-4741).
- **[SRC]** For each cell row i of matrix μ and each combination u < τ: comb(μ, i, u) = Σ_c Θ_μ[c][u]·cell(μ, i, c). The prover commits array `ZZ` (τ rows × 2·mz columns, unpacked F elements, mz = total cell rows of the segment's matrices): low digit (10 bits) and high digit (8 bits) of comb + 2^17. Digits exist only if −2^17 ≤ comb < 2^17 ("the combination's window") — `docs/format/11-1-machinery.md:1129-1133`, constants `LBZ = 17`, `T2D0 = 10`, `T2D1 = 8` at `:1095-1107`.
- **[SRC]** A dedicated second lookup per segment (two calls: range 2^10 and range 2^8) checks all 2·τ·mz digits; its multiplicities are 32 bit-planes in array `BZ` (32 × 2^11) — `11-1-machinery.md:1135-1145, 1173-1205`.
- **[SRC]** Two families of linear equations tie digits to committed data, all batched under powers of one challenge χ into the segment's single linear claim (no sumcheck of their own):
  - packed row: `val(u,crow) + 2^20·val(u,crow+1) + 2^40·val(u,crow+2) − Σ_c Θ[c][u]·M[i'][c] = 0`;
  - read: `Σ_r φ_f[r]·val(u, crow+r) − Σ_c Θ[c][u]·U3[at(f) + c·nb(f) + b] = 0`
  — `11-1-machinery.md:1231-1262`; the same two equations in `blocks/iop/rng.h:385-397`.
- **[SRC]** How the verifier evaluates Θ: it never needs a succinct extension of a tensor-sized object. Weights are products: on a packed matrix, powers of χ^τP over packed rows times `colw(c) = Σ_u χ^u·Θ[c][u]` over columns; on the digits, powers of χ over u times a vector over columns — `blocks/iop/rng.h:395-397, 421-441`; `11-1-machinery.md:1073-1077, 1282-1290`. Verifier work is O(k·τ) per matrix (k ≤ 8191 columns, `KCAP`), independent of the number of rows.
- **[SRC]** "Reads": `U3[n]` is meant to be Σ_r φ_f[r]·cell(mat(f), b·len(f)+r, c), a partial evaluation along the row (token) axis under a public weight vector fixed before Θ. "Other blocks need reads because no linear form gets a single cell back from a packed entry" — `blocks/iop/rng.h:53-60`; `11-1-machinery.md:1121-1127`. The range test therefore also proves that the reads other sub-protocols consume are sums of the same small integers that the packing holds.

What it proves and the slack
- **[SRC]** Stated purpose: "one integer matrix Y with |entries| < 2D, a looser bound than honest cells meet, has this packing and these reads"; with 2D = 2^(10+8) the bound is (−2^18, 2^18); "The test does not state that a cell is a byte" — `blocks/iop/rng.h:6-11`, `11-1-machinery.md:1437-1441`.
- **[PAPER]/[LEAN]** The request relation is defined with "cells of absolute value below the relaxed bound 2^18"; honest bound is 2^7; one Lean theorem shows constraints mod p with relaxed-bound cells imply the model conditions, a second passes from honest to relaxed bound — paper.txt:875-895, 1059.
- **[SRC]** Honest-prover design constant (f2): (8191 + 1)·2^14·2^7 ≤ 2^34, "so that an honest prover's combination leaves its window only with a small chance" — `11-1-machinery.md:1471-1473`.

Completeness
- **[LEAN]** `pr_win_le` (`lean/Prob/Window.lean:343-365`): if all cells have |Y| ≤ b and no matrix has more than n₂ columns, Pr[some combination leaves [−t, t)] ≤ n_Ψ · 2·exp(−t²/(n₂·b²)). At t = 2^17, b = 2^7, n₂ = 2^13 the exponent is 128 (`ref_exponent`, `:374-378`) and one entry fails with probability ≤ 2e^−128 ≤ 2^−183.66 (`ref_entry`, `:386-392`). `lean/GAPS.md:874` notes this general bound "is proved but not applied at the IOP".
- **[LEAN]/[PAPER]** Overall completeness of the Lean prover on served requests ≤ 2^−40 (non-interactive) / 2^−41 (interactive), which bundles the range-test window, an all-zero Θ column, zero batching coefficients and proof of work — paper.txt:130-133, 169-180; `lean/GAPS.md:791`.
- **[SRC]** When an honest combination leaves the window "there is no honest proof with these sampled entries"; the request is answered "failed" — `11-1-machinery.md:1477-1481`, `docs/protocol.md:195`. Also, an all-zero column of Θ (probability exactly 2^−τ per column) makes the verifier give no acceptance — `docs/format/FORMAT.md:2468`, `11-1-machinery.md:1406-1413`.

Soundness argument
- **[SRC]** Source comment: the round's error is 2^−N for N combinations. A column is "explained" if one integer column with entries in (−2D, 2D) has this packing and these reads. Packing, reads and φ are fixed before Θ, so the first unexplained column is fixed; with all other entries of Θ fixed, no two neighbouring values of that column's entry Θ[c][u] can both let combination u pass (their difference would explain the column), so the passing values lie in {0} or {−1, 1}, probability ≤ 1/2 each, independently across the N combinations. "Nothing is assumed about Psi: a lane of YΘ may overflow and carry." — `blocks/iop/rng.h:344-359`.
- **[SRC]** Ordering is load-bearing: "a prover that knows Theta can alter a read by a vector on which all N combinations vanish" — `blocks/iop/rng.h:338-342`, `11-1-machinery.md:1157-1171`. Beyond unique decoding, "fixed as one object" rests on the answered OOD samples.
- **[SRC]** Provenance and caveats: adapted from Lemma 2.5 / Lemma A.1 of Lyubashevsky–Nguyen–Seiler (ePrint 2020/1448, §2.7) and Gentry–Halevi–Lyubashevsky (ePrint 2021/1397, §3.4, Lemma 3.4, the 1/2-1/4-1/4 distribution for 128 combinations); "argued on paper and not refereed"; "A form that takes packing and reads apart has a hole; this one has been tried with exhaustive searches at toy sizes" — `blocks/iop/rng.h:23-25, 354-376`.
- **[LEAN]** The 2^−128 error of the Range-test round at every admissible configuration is machine-checked (Proposition 5.14) — paper.txt:5640-5641 [PAPER reporting a Lean result]; Table 10 lists it as "the share 2^−128 of all matrices; 128 independent columns" (paper.txt:3524). **[SRC]/[PAPER]** A stricter union bound over all tested columns gives 113.44 bits (printed by the C++ planning call), and a list-size factor would give ≈ 122.2 bits — paper.txt:5644-5661; `blocks/iop/rng.h:360-364`.
- **[SRC]** Reported false acceptances in tests of the general block when its layout or plan was described twice inconsistently (a cell of 1000 accepted under bound 32; 33 columns × 1 combination run under a plan for 1 × 33) — `blocks/iop/rng.h:172-176, 305-318`. `cp_prove`/`cp_verify` run a second implementation, not this header (`rng.h:20-21`).

From "small cells" to "integer equations"
- **[SRC]** Small cells alone are not enough: the verifier also tests "no-overflow conditions" on the public parameters so that identities holding mod p hold over the integers; "it is not proved that the programs' conditions are enough for the programs' equations" — `docs/protocol.md:159`. The technique is credited to Gentry–Halevi–Lyubashevsky §3 "congruences that hold over the integers" (paper.txt:4846-4849).

Zero knowledge
- **[SRC]/[REPORT]** The digits and multiplicities are committed under the same masked encoding; the honest failure event depends on the cells and on Θ and "the source counts its chance in the error of hiding" (`11-1-machinery.md:1477-1481`); a hiding condition `range-checks` computes floor(14426·2^34 / (10000·2^14·k_μ)) − 1 − clog2(m_μ) − clog2(τ) per matrix and requires the minimum (less further terms) to be ≥ `sec` (`11-1-machinery.md:1384-1391`). The report says a rejected request might leak about the weights and a retry with fresh randomness is planned (report §7, "Approximate range checks").
- **[LEAN]/[PAPER]** Zero knowledge is proved "with request leakage": one bit per request (served or not) is revealed — paper.txt:134-140, 170-174.

### Inferences
- **[INFER]** Slack law. With b the honest bound and k the number of columns, the window half-width must satisfy t² ≥ 128·k·b² for the 2e^−128 tail, so t = b·√(128k) and the proven bound is 2t: slack = 2·√(128·k) ≈ 22.6·√k (2^11 at k = 2^13). The constant 14426/10000 ≈ 2·ln 2·... in the hiding condition is consistent with converting e^−x to bits (1/ln 2 = 1.4427).
- **[INFER]** Cost law. Per cell row of k cells the test commits 2τ = 256 digit field elements (unpacked) and performs 256 small-table lookups, whatever k is. At the full-size feed-forward segment, matrix `af` has ≈ 5,990 columns (1,149,952 cells per token per 4-layer group, 3 parts of 2^16 rows; computed from `11-2-feed-forward-segment.md:48-52` and `policy.txt`), so the range test costs ≈ 0.043 digit lookups per cell, versus one lookup per cell in the "simplified IOP". `ZZ` has 128 × 2 × 499,712 ≈ 1.28·10^8 elements (mz from `11-2:224`), roughly a quarter to a third of the segment's ≈ 4·10^8 packed cell elements; so the check is not free, it is about a 25–35 % commitment overhead on this segment, bought with the 3-to-1 packing it enables.
- **[INFER]** Why bytes. The slack is multiplicative in the honest bound, and the packing radix must exceed 4× the window. Byte cells keep the window at 18 bits and allow three lanes in 64 bits; wider cells would need a wider window, more digits per combination and fewer lanes.
- **[INFER]** Use with virtual tensors (answer to the open design question in `docs/research-directions.md` §7.3): yes, structurally. Nothing in the construction needs the tensor to be a committed codeword; it needs (a) the tensor to be a fixed field-valued object before Θ is drawn, and (b) a way to check Σ_c Θ[c][u]·Y[i][c] = Ψ[i][u]. In a sumcheck system (b) is one sumcheck over the column index: Σ_c Θ̃(c, r_u)·Ỹ(r_i, c) = Ψ̃(r_i, r_u), ending in an MLE evaluation claim Ỹ(r_i, r_c) (exactly what a virtual tensor supports) and Θ̃(r_c, r_u), which the verifier computes in O(k·τ) from the transcript-derived trits — no succinct structure needed because Θ is shared by all rows. Ψ's digits are the only new committed object. For (a), a jolt-atlas virtual output is determined as a field vector by the committed remainder digits and the operands, so drawing Θ after those commitments suffices; the FlashProve comment about "a form that takes packing and reads apart has a hole" is specific to packed commitments and does not arise when Y is opened by MLE evaluation directly.
- **[INFER]** Sizing for jolt-atlas. With 32-bit honest values (b = 2^31) and a k-column tensor, t = 2^31·√(128k); for k = 1024 the window is ≈ 2^40.5 wide per side, i.e. ≈ 11 four-bit digits per combination, 128 combinations per row: ≈ 1,400 digits per row of k outputs, against 8·k clamp digits today. Break-even is k ≈ 176; at k = 1024 it is ≈ 5.8× fewer digits, at k = 4096 ≈ 22×, and the proven bound (≈ 2^42) is harmless in a 128-bit field. Rows should be taken along the longest axis. With 8-bit digits the constant halves.
- **[INFER]** What it cannot replace. It shows "no wrap-around", not `saturating_clamp_i32`. FlashProve handles this by making the model a partial function (section 6): values that feed only linear ops are covered by the approximate check plus public no-overflow conditions, and a request whose values leave their intervals simply has no proof. Adopting the check for the 8 output-clamp digits therefore changes jolt-atlas's contract from "saturate" to "undefined outside range" on those tensors (or keeps exact clamps only where a consumer is non-linear).

### Gaps
- The written proof of the 2^−N bound for the packed-plus-reads form lives in the non-public internal technical report; only the source comment's sketch and the existence of a Lean round-error proposition were available. The Lean files under `lean/Johnson/Desc/First/K8/` and `lean/Johnson/K8Q*R/` were located but the specific soundness theorem was not read.
- Whether fewer combinations with grinding, or a larger coefficient alphabet, were considered is not discussed anywhere; `work smallness 0 0 0` shows no proof of work is assigned to this round.
- The retry mechanism for honest failures is announced (report §7) but not implemented in the release.

## 3. Exact rounding: how the rounding right shift is proven exact, and which values still get a per-value exact check

### Takeaway
Every rounding site commits the quotient (as byte limbs) and at most the part of the remainder above bit 16; the low 16 bits of the remainder are never committed. Exactness comes from one lookup into a 2^16 range table whose key is a virtual linear form — the scaled remainder `A + 2^(k−1) − 2^k·Q` minus the committed high part — plus one small lookup on the high part. Quotients that feed a clamp or activation get a second exact lookup through that table; quotients that feed only linear operations (the residual stream, attention output) get no exact per-value check at all.

### Cited Findings
- **[SRC]** "Every rsh(A, k) above is committed as a quotient Q and a remainder rem = A + 2^(k−1) − 2^k·Q with 0 ≤ rem < 2^k. A site has a digit form h … With h = 0 nothing of the remainder is committed, and k is at most 16. With h = 1 or 2 the cells hold rh, the remainder's part from bit 16 on minus an offset: rem = low + 2^16·(rh + ofs_h) with 0 ≤ low < 2^16 … rh has h limbs. k is at most 24 for h = 1 and at most 32 for h = 2." — `docs/format/11-2-feed-forward-segment.md:379-385`.
- **[SRC]** Lookup keys: `SK(A, Q, k, h, rh) = 2^lift(k)·(A + 2^(k−1) − 2^k·Q) − 2^16·(rh + ofs_h)` must lie in the 16-bit range table (lift(k) = 16 − k for k < 16, scaling a short remainder up so its range is exactly 2^16); `HK(rh, k, h) = 2^(top_h − max(k,16))·(rh + ofs_h)` must lie in an 8- or 16-bit range table (scaling so the high part's range is exactly 2^(k−16)) — `11-2-feed-forward-segment.md:296, 604-605`. These are used at every site: gate/up projections (G, U, GH, UH), queries/keys after RoPE (QK, QKH), values (V, VH), attention output projection (O, OH), down projection (D, DH), norms (N1, N1H, N2, N2H), router (LR, LH) — `:607-636`.
- **[SRC]** In the keys, A is not committed: it is an inner product of committed activations with committed weights (or a product of two committed vectors), supplied to the lookup's key claim through a sumcheck ("three pieces of a key": line piece, inner products, terms) — `11-2-feed-forward-segment.md:638-645`. "The keys are never sent" (`11-1-machinery.md:132`).
- **[SRC]** Exact per-value checks on quotients, where they exist, are fused with the consumer's table: clamp table row `t + 2^28·(clamp(t − 32768, ±2047) + 2048)` with key `(aw + 2^15) + 2^28·(an + 2^11)` (calls CN1, CN2, CQK, CV); SiLU table key `(y + 2^15) + 2^28·(sl + 2^12)` (F); `up + 2^15` in R16 (UT); router `2·(lr + 2^14)` (LT) — `11-2-feed-forward-segment.md:612, 622-636`; table rows at `11-1-machinery.md:323-328`. One 2^16-row table lookup proves both "input is 16-bit" and "output = f(input)".
- **[SRC]** Sites whose quotient has no exact range lookup: O and D, whose quotient is the residual-stream difference `str_(2lam+1) − str_(2lam)` (5 byte limbs per stream value, `xl 5`) — `11-2-feed-forward-segment.md:617-618, 415`; XR (`sc·mn + 2^15 − 2^16·xr` in R16, with `xr` 2 limbs and no other key) — `:628`; attention output `o` (only remainder keys WL/WH) — `docs/format/11-3-attention-segment.md:434-435`. The stream's magnitude is bounded only at the next norm, by the norm's digit row (range condition 1, Vx + eps < 2^78, which implies |x| < 2^39) — `docs/model.md:298-307`.
- **[SRC]** Division by a variable denominator (attention): `rem = 2·acc + Zd − 2·Zd·o` must satisfy 0 ≤ rem ≤ 2·Zd − 1; proved two-sidedly with committed high bytes `rh = floor(rem/65536) − 128` and `rhp = floor((2Zd − 1 − rem)/65536) − 128`, two R16 lookups on the low parts (call WL) and one lookup pairing the two bytes (call WH) — `11-3-attention-segment.md:321-323, 398-399, 434-435, 455-457`.
- **[SRC]** Norm (isqrt and reciprocal) uses the same two-sided pattern per token, not per element: digits of `l1 = Vsq + eps − sig²`, `h1 = 2·sig − l1`, `rr = 2^M + floor(sig/2) − R·sig`, `rq = sig − 1 − rr`, with carries, in a "row of digits" of NR = 99 byte cells per token per norm, each digit in an 8-bit range lookup with a per-digit multiplier `mul_j` that narrows its range (key `mul_j·D_j`) — `11-2-feed-forward-segment.md:544-576, 621`.
- **[PAPER]** "Softmax, attention, and rounding by a lookup of the remainder follow [zkLLM, QSL25, CWS24]" — paper.txt:4919.

### Inferences
- **[INFER]** Per matmul output element at the default configuration (e.g. `up` with ku = 20, huD = 1): committed cells = 2 (quotient limbs) + 1 (remainder high byte) = 3 bytes = one packed field element; lookups = 3 (U: 16-bit low remainder; UH: 8-bit high remainder scaled; UT: 16-bit quotient range). For a gated unit (gate + SiLU, `gcl 1`): 7 cells, 5 lookups, of which one is the activation itself. For a norm output: 6 cells (aw 2, ra 2, an 2), 3 lookups (N1, N1H, CN1). The jolt-atlas equivalent today is 12 committed one-hot digits (rescale) and 13 more for an activation.
- **[INFER]** The remainder check is a lookup on a virtual address. In jolt-atlas terms: the range-check address is the linear form `acc + 2^(k−1) − 2^k·q` itself, not a committed decomposition of a committed remainder. With Shout-style one-hot addresses the address digits are the committed object, so this specific saving (zero commitment for the low 16 remainder bits) does not carry over directly; it would carry over to a LogUp/grand-product range check over a virtual column (roadmap D4), whose only commitment is multiplicities.
- **[INFER]** Scaling the key (`2^lift(k)`, `2^(top−k)`, `mul_j`) is how one table size (2^16 or 2^8) enforces ranges that are not a multiple of the digit width — the exact issue flagged in roadmap B1 ("a bound whose width is not a multiple of the digit size has to be enforced exactly, for example by also checking a shifted copy").
- **[INFER]** The division of labour is: remainders — always exact, by lookup; values entering a non-linearity or clamp — exact, by the fused (input, output) table; limb representations and linearly-consumed values — approximate range check plus public no-overflow conditions. The technical report's sentence "instead checks random sums" refers to the limbs, not to remainders or table inputs.

## 4. Lookups: argument, table sizes, multiplicities, cost per lookup, soundness at large sizes

### Takeaway
A grand-product (multiset-equality) lookup proved by GKR-style product trees with zero-knowledge sumchecks: Π_i (α − key_i) = Π_j (α − tab_j)^mu_j. Keys are virtual (never committed); only the multiplicities are committed, in bits (32 bit-planes per table row). Up to 8–16 "calls" with different tables run as one lookup via a random shift. Tables have 2^8, 2^10 or 2^16 rows and pack (argument, value) into one field element. Instance size costs nothing in soundness because α lives in the 192-bit extension.

### Cited Findings
- **[PAPER]** "Lookup, for lookup keys ky_i and a table (tb_j). P has sent, in bits, the multiplicity mu_j of each tb_j. V samples ϖ. The claim Π_i (ϖ − ky_i) = Π_j (ϖ − tb_j)^mu_j, with a public factor for padding, is reduced along the two trees of products, by masked sumchecks, to claims on the lookup keys and the bits; one more shows that the bits are bits." — paper.txt:4552-4555. Sources: grand products [GKR08; Thaler13 §5.3.1]; several tables in one [BCGJM18 App. B.5/B.6; GW20 §4] — paper.txt:4838-4845.
- **[SRC]** Step list of one lookup: (1) shift θ if more than one call; (2) comparison point α; (3) "tie of the two sides' roots": 31 variable-free sumchecks; (4) a point joining the 32 planes' roots; (5) key side: product levels with m = 0..v−1 variables; (6) table side: product levels with m = 5..4+dL variables; (7) table leaves: a sumcheck with dL rounds of degree 2 and 5 of degree 1; (8)–(9) "the bits are bits" sumcheck — `docs/format/11-1-machinery.md:158-168`. A product level with m variables is m equality rounds of degree 2 plus a `LINE` round (`:110-118`).
- **[SRC]** "The keys are never sent. The multiplicities are committed in bits, in 32 planes." Bit (t, c, j) is bit j of the multiplicity of row t of call c; the bits are cells of a committed matrix (b / bA / bH) packed like every other matrix — `11-1-machinery.md:132-133, 188-200`.
- **[SRC]** Call structure and limits: NC ≤ 16 calls per lookup (≤ 8 in a feed-forward segment's list, ≤ 12 in attention); call c has 2^(n_c) keys and a table of 2^(k_c) rows; keys are split into trees of 2^dT (dT ≤ `lidb`, 28 at full size), at most 256 trees; v = dT + rK < 32; 2^(dL+32) < p — `11-1-machinery.md:126-132`; `11-2:202-203`; `11-3:68-70`. Worked full-size example: feed-forward calls have 27, 27, 27, 28, 27, 27, 26, 26 key bits (v' = 30, i.e. ≈ 2^30 key slots per feed-forward segment); attention calls 27, 27, 26, 25 (v_A = 29) — `11-2:219-227`, `11-3:200-206`.
- **[SRC]** Tables: ranges of 8, 10, 16 bits; clamp `t + 2^28·(clamp + 2048)`; SiLU `t + 2^28·(s(t) + 4096)`; sigmoid `t + 2^17·16·round(4096·sigmoid)`; head exponentials `u + 2^16·EX[u]`; attention `KR` (two bytes + flag "≥ 2^sh"), `WH` (two bytes), `KFD` (exp table fused with comparison and causal-mask rows). "The other tables … have 65,536 rows each, and a row packs an argument and a function's value into one number below p." — `11-1-machinery.md:316-334`.
- **[SRC]** Padding keys are a fixed table row and are excluded from the multiplicities; one claim checks that multiplicities sum to the number of non-padding keys — `11-1-machinery.md:133-155, 1275`. The source records that loosely described padding once let a key outside the table through in a test (`:139-145`).
- **[PAPER]** Round error for the lookup's comparison point: bad challenges are "roots of a polynomial", count 2^(k+1) − 1 for trees of depth k, over E — paper.txt:3521-3523 (Table 10).
- **[REPORT]** "two thousand sumchecks per inference request, accounting for 90-95% of all the interaction rounds" (report §5.1, tr.txt:332-333).

### Inferences
- **[INFER]** Cost per lookup: zero committed elements per key; prover work is the product tree over keys in E (≈ 2 field-extension multiplications per node per level for a degree-2 GKR layer with Gruen-style eq handling — [Gru24] is cited for round polynomials, paper.txt:4829-4830) plus the linear-form evaluation that produces the keys. Committed per table: 32 bits × 2^16 rows per call (≈ 2·10^6 bit cells ≈ 7·10^5 packed elements), independent of the number of keys.
- **[INFER]** Multiplicities-as-bits makes the table side a product of (1 + b_{t,j}·((α − tab_t)^(2^j) − 1)) terms: 32 planes each with its own root, tied by the 31 variable-free sumchecks. This avoids committing field-sized multiplicities and avoids fractional (LogUp) sums entirely.
- **[INFER]** Soundness at scale: the roadmap/research-directions concern (§4.4, "LogUp leaves ≈ 100 bits at 2^28 elements over a 128-bit field") is answered here by field size, not by argument choice: 2^31/2^192 = 2^−161. For jolt-atlas over Fp128 with 128-bit challenges, a grand product over 2^28 keys leaves ≈ 100 bits; FlashProve's approach implies either an extension-field challenge or accepting grinding.
- **[INFER]** The lookup volume is the bulk of the non-commitment work: ≈ 2^30 key slots per 4-layer feed-forward segment for 1,024 tokens (≈ 2.6·10^5 lookups per token per layer) and ≈ 2^29 per attention segment.

## 5. Per-op protocols

### Takeaway
One trace covers all 1,024 positions. Matmuls with committed weights are Thaler-style: lookup-key claims at a random point become one batched inner-product sumcheck whose weight side is merged into a single linear claim on the weight table. Attention commits five byte cells per (query, key) pair and nothing for the score; max is a committed argmax index in bits; softmax normalization is folded into the ·V division. Norms are per-token digit rows. Router and vocabulary argmax are indicator/margin arguments with range lookups.

### Cited Findings
Matmul with committed weights
- **[SRC]** The pre-rounding accumulators A are never committed; the lookup's key claim at point (zt over tokens, zj over features) is a sum of inner products, proved by "the batched inner products: a sumcheck with lamS plain rounds of degree 2" over Σ SA[n]·SB[n], where SA holds partial evaluations of activations (entries of U3) and SB holds weights; lamS = 23 at full size — `docs/format/11-2-feed-forward-segment.md:80, 110-113, 752-799, 226`. Each panel leaves a weight claim; NCL = 6·Lam + 4·LamM (+1 embedding) weight claims per segment are batched by "the merge": one `BAT-sigma` and a sumcheck with lkW = 18 plain rounds, leaving one row on the stored table — `11-1-machinery.md:202-218`, `11-2:85, 824-852`.
- **[PAPER]** Sources: Thaler13; Liu–Xie–Zhang 2021 §4.3; zkLLM — paper.txt:4850-4851. The first part of the request IOP ends in one claim ⟨h ⊗ eq(ψ,·), A⟩ + η = b on the digit matrix; the prover then commits w = hᵀA and a batch-shared step checks all requests' w against one opening of the table (Construction D.7) — paper.txt:953-959, 4560-4593; `docs/protocol.md:163-187`.
- **[SRC]** Gated products `hh = sl·up` are "not committed" (`11-2:357`); they are handled by product-level sumchecks (steps 12, 14), and the down projection reads them through H1 only (`11-2:775, 819-821`).

Attention and softmax
- **[SRC]** Computation: sc(i,j) = ⟨q_i, k_j⟩ (12-bit clamped operands, 128 channels); Mx(i) = sc(i, ib(i)) with ib(i) ≤ i committed as lt bits; Df = Mx − sc; u = floor(Df/2^sh); ew = Tt[u] if u < u0 else 0; Zd = Σ_j ew; acc = Σ_j ew·v_j; o = round(acc/Zd) — `docs/format/11-3-attention-segment.md:302-325`; `docs/model.md:201-212`. Table Tt[u] = rne(2^12·exp(−u/2^8)) (`S 12`, `rx 8`), sh = 8 at the default (`policy.txt:95-96,127`).
- **[SRC]** Committed per pair: five cells — two bytes of rm (= Df mod 2^sh-related remainder, 0..65535), a flag (rm ≥ 2^sh), and two cells of the weight ew — `11-3:359-370`. Per pair two lookups: `KR` on (c0, c1, c2) and `KFD` with key `Df − rm + 2^32·flag + 2^33·ew`; a `KFD` row t < u0 is `t·2^sh + 2^33·Tt[t]` (so Df − rm = t·2^sh and ew = Tt[t]), and rows t ≥ u0 encode "ew = 0 and Df ≥ cutoff" in steps of ρ = 65536 − 2^sh — `11-1-machinery.md:331-334`, `11-3:428-457`. The table also forces Df ≥ 0, i.e. Mx is a true maximum.
- **[SRC]** Scores are virtual: the `KFD` key claim is reduced by degree-3 sumchecks K_u of the form Σ W·A·B with A a partial evaluation of q and B of kx; further sumchecks SE (Zd·o), VM/VD (ew·v), SF/SD (Mx = sc at the committed argmax, with the product over index bits Π_k eq1(ibit_k, bit_k(j)) giving rounds of degree up to lt + 2), HB (index bits are bits) — `11-3:619-659`, rounds table `:148-174`.
- **[SRC]** Causal mask and layout: the T × T pairs are cut into Bt × Bt tiles (lB = 6, Bt = 64); only diagonal tiles (region D) and below-diagonal tiles (region M) have cells; in a diagonal tile, pairs with j > i get Df + Om_sh so the table returns weight 0 — `11-3:327-349, 441-446`. `IX` key 2^(16−lt)·(i − ib(i)) in R16 forces ib(i) ≤ i (`:436, 457`).
- **[SRC]** Grouped-query attention: 40 query heads read 8 key-value heads (`docs/model.md:201`); "An attention segment reads no weights of the model" (`11-3:38`).

Normalization (RMSNorm)
- **[SRC]** N(x): Vx = Σ x²; σ = isqrt(Vx + eps); Rc = floor((2^M + floor(σ/2))/σ); w = rq(x·Rc, K); output clamp(w; 2047); gains and √d are folded into the weights — `docs/model.md:168-182, 413-437`. Proof: sums of limb products with carries (the stream has 5 byte limbs, so Vx is assembled from 9 limb-product sums), a per-token row of 99 byte digits holding Vsq, carries, σ, l1/h1, R, rr/rq, and seven row products (a², ab, b², Rlo·a, …), with token sumchecks of degree 2 — `11-2:30-31, 73-78, 544-576`. The per-element part is only the rounding site N1/N2 plus the clamp lookup CN1/CN2.

SiLU and the gate
- **[SRC]** One 2^16-row table: Ts[c] = clamp(rha(64·silu(c/2^8)); 4095) for c clamped to ±64·2^8; with `gcl 1` the 16-bit-plus gate value is split gw = g0 + 256·gh, gh is clamped to ±127 by a second table (CG) "where Ts is constant, so the clamp only saturates", and the SiLU table is read at g0 + 256·gc — `docs/model.md:138-146, 228-238`; `11-2:354-357, 625-627`.

MoE router and expert selection
- **[SRC]** Router logits lr (16-bit, clamped form with `rcl 1`); `sel(e,t)` ∈ {0,1} via key 128·sel in R8; Σ_e sel = 1 (one claim per layer); mr = Σ_e sel·lr; argmax with lowest-index tie-break via key `mr − lr(e) − Σ_{e' > e} sel(e')` in R16 for every e; scale sc = Sig[mr] by a sigmoid table keyed `(mr + 2^14) + 2^17·sc` — `11-2:364-371, 631-636, 135`; `docs/model.md:246-256`.
- **[SRC]** Routed expert's matmuls: accumulator = Σ_e Σ_k sel(e,t)·W_e(k,x)·xr(k,t); proved by "selector" panels whose weight claim binds the expert index group `e` with s1 = Σ_ri selt'·EI[ri] — `11-2:372-377, 781-782, 806-817, 846-847`. **[REPORT]** "the verifier's queries do not reveal which expert ran" and prover work "proportional to the experts that actually ran" (report §5.2).

Embedding, RoPE, output head
- **[SRC]** Embedding: tokens are public, so the embedding is a weight claim with the public sparse vector tokw[v] = Σ_{t: tok_t = v} eq(ztE, t) on the vocabulary index; no lookup argument — `11-2:865-868, 848`.
- **[SRC]** RoPE: integer tables C, S = round(2^12·cos/sin) are public; the rotation is applied before the rounding shift and is absorbed into the verifier-computed factor `rot[]` of the Wq/Wk weight claim (Ct, St = Σ_t eq(rt, t)·C/S), so the unrotated projection is never committed; kq/kk remove the 2^12 — `11-2:334-339, 854-863`; `docs/model.md:134-135, 189-198`.
- **[SRC]** Head: final norm at every position; logits lam_t[v] = Σ_k act[t][k]·Wh[k][v] are virtual; for every vocabulary entry a margin Mg[t][v] = lam_t[win_t] + (cost terms) − lam_t[v] − [v < win_t] is written in three digits (8, 16, 16 bits, overlapping, prover-chosen) each range-looked-up, plus a table value ex[t][v] = EX[K_1]; four policy equations bound costs — `docs/format/11-4-output-head.md:252-301, 33, 98-112`. Exact match is the case where every margin is ≥ 0 with zero slack (`docs/protocol.md:43`; `docs/model.md:276-281`). The next token is sent in the clear as one unmasked scalar (`11-4:51-57`).

One pass, segments, causal structure
- **[SRC]** "Only step 4 of section 6 reads other positions, and only j ≤ i. So every value at position t depends only on tok_0 .. tok_t" — `docs/model.md:288-290`. - **[SRC]/[PAPER]** 48 layers in groups of Lam = 4 (`ll 2`): each group has one feed-forward segment (norms, all projections, RoPE, router, MLPs, residual stream) and one attention segment; plus the head: G = 25 segments — `11-2:10-21`, `11-3:20-28`, paper.txt:708.

### Inferences
- **[INFER]** FlashProve's attention is essentially roadmap item C3 already built: unrescaled scores as a virtual accumulator, max entering like a bias, one fused lookup that is simultaneously the range check on max − score, the exp table and the causal mask, normalization moved into the ·V division, committed argmax. The differences: the argmax is committed as log T index bits (with a high-degree sumcheck) rather than a one-hot, and the per-pair commitment is 5 bytes (≈ 1.7 packed elements) versus C3's estimated 10–12 one-hot digits.
- **[INFER]** Table-fusion pattern: wherever a comparison, a clamp and a function meet, FlashProve builds one 2^16-row table whose rows encode all three with disjoint bit fields (2^28, 2^32, 2^33, 2^40 offsets) and feeds it one virtual key. This is roadmap B2/B3 generalized.
- **[INFER]** RoPE-in-the-weight-claim is the committed-weights analogue of pushing a public linear map into the einsum: applicable in jolt-atlas whenever a public tensor multiplies a matmul output before the rescale.
- **[INFER]** Vocabulary argmax costs 6 cells and ≈ 3 lookups per (position, vocabulary entry), i.e. ≈ 2·10^8 margins for 1,024 positions; it is computed at all positions even when one token is checked.

## 6. Quantization: bit widths, scales, 4-bit weights, accumulators, accuracy

### Takeaway
All scales are per-site, per-layer powers of two fitted on calibration text. Activations are 12-bit after clamping (16-bit "wide" before), the residual stream is up to 40 bits in five byte limbs, weights are 13-bit integers (the 4-bit GGUF codes are decoded to floats and re-quantized per tensor), and the model is a partial function defined only where eight kinds of intermediate value stay in fixed intervals. The integer model's greedy token differs from float32 at 6.81 % of positions.

### Cited Findings
- **[SRC]** Rounding primitive rq(a, k) = floor((a + 2^(k−1))/2^k) (round-to-nearest, ties up); "The activations a, m, v and aF, and the queries and keys, are clamped to 12 bits with sign: clamp(x; 2,047)" — `docs/model.md:35-47`.
- **[SRC]** Scale file: per layer 13 words (shifts kq, kk, kv, ko, kg, ku, kd; norm exponents M1, K1, M2, K2; softmax key shift sh; RoPE flag) plus kr, kgR, kuR per MoE layer — `docs/model.md:103-121`. **[PAPER]** Default values 29, 29, 17, 17, 16, 20, 19, 44, 30, 44, 30, 8 and (17, 16, 20); valid ranges e.g. kv, kg, ku ∈ 1..24, kd ∈ 10..19, 24 ≤ M ≤ 47, 17 ≤ K ≤ 32 — paper.txt:4459-4466, 641-650.
- **[SRC]** Weights: no biases, no norm gains (gains and constants √d/64, 1/√dh are multiplied into the matrices). Per tensor, exponent e is the largest integer with RNE(2^e·max|π|) ≤ 4,095 and w = RNE(2^e·π), so |w| ≤ 4,095; embedding entries below 2^30 (file writes ≤ 21 bits). Source blocks Q4_K/Q5_K/Q6_K/Q8_0/F16/BF16/F32 are decoded with exact float32 steps first — `docs/model.md:81-101, 368-452`.
- **[SRC]** Range conditions defining the model's domain: Vx + eps < 2^78; norm quotient, wide q/k, wide v, router high part, up projection in −32,768..32,767; gate high part in −16,384..16,383; stream |x| < 2^39. The provers accept slightly less (two limbs end at 32,639; five limbs at 547,599,908,735) and answer `failed` in between — `docs/model.md:292-317`.
- **[SRC]** `cp_commit` bounds, from the weights and scales alone, what any prompt can drive these values to ("argued, not proved") — `docs/model.md:314-317`, `scales/worst-case-bounds.md`.
- **[SRC]** Public tables are generated with IEEE float64 (correctly rounded exp/cos/sin/pow), then frozen by digests in the parameter file — `docs/model.md:123-166`; "The format does not define these values by integer arithmetic" (`11-1-machinery.md:336-340`).
- **[PAPER]** Accuracy: greedy token differs from the 16-bit weights in float32 at 6.81 % of positions on 216 texts and 9.41 % on the 24 natural passages (Python implementation, no proofs, WikiText-2-based, the calibration distribution); no task benchmark — paper.txt:2515-2521; same in `guide/performance.md:33`. Of 96 greedy replies from each of two float engines (16-bit, FP8), none matches the integer model at every token (paper.txt:2377-2379). On 544 windows from 96 prompts no range condition failed at the public 4-bit weights (counted outside Lean, other programs) — paper.txt:4499-4502.
- **[PAPER]** 400.7 billion committed weights; one token's forward pass uses 16.15 billion — paper.txt:2532-2535.

### Inferences
- **[INFER]** "4-bit weights" does not mean 4-bit arithmetic in the proof: the committed objects are 13-bit integers in two signed bytes. The byte-limb representation, not the source bit width, sets the commitment cost (2/3 of a field element per weight in the table).
- **[INFER]** Accumulator width: a matmul of 12-bit activations with 13-bit weights over d = 5,120 (or f = 16,384) terms is ≤ 2^(11+12+14) = 2^37, times 2^lift ≤ 2^15 in the key, comfortably below p ≈ 2^64 but not by a wide margin once products of three (sel·W·xr, s·u·Wd) are involved; this is what the per-parameter no-overflow tests guard. A 64-bit field only works because of 12-bit clamping at every matmul input.
- **[INFER]** FlashProve's quantization is the design research-directions §6 calls "our own quantization at narrow width with power-of-two per-tensor scales", and it pays a measurable accuracy price (≈ 7–9 % top-1 disagreement), which is the number to beat or match in the planned tracer experiment (§9 step 2).
- **[INFER]** Platform floating point in table generation is a deliberate difference from jolt-atlas's pure-integer `atlas_trace::semantics`; FlashProve pins the result by digest instead.

### Gaps

## 7. Engineering: segments, memory, GPU kernels, what dominates prover time

### Takeaway
The repository, guides, paper and report contain throughput, memory and size totals but no breakdown of prover time by stage. Structurally, proving is segment-by-segment with a fold of each closed segment into a short carried commitment, and the weight table is recomputed per batch rather than stored.

### Cited Findings
- **[SRC]** Throughput (public 4-bit weights, one H100 80 GB, 24 CPUs, 1,024-token windows, masking on, n = 3): 17.41 / 76.34 / 111.23 / 123.31 tokens/s at 1 / 8 / 24 / 64 requests per batch; 9.2 s per request at 24; batch latency 220.7–225.9 s; start-up 68–79 s; committing ≈ 39 min (2,307–2,344 s); proof 18.78 MB; client download 6.24 MB; provider keeps 2.15 GB; C++ verifier ≈ 21 s on one thread, 3.53 GB; host memory 269.7 GB serving, 299.6 GB committing; 64 per batch reaches 80.6 of 81.6 GiB of GPU memory and failed on synthetic weights — `guide/performance.md:8-29` ([FP](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/guide/performance.md)); paper.txt:2231-2294.
- **[SRC]** "up to six requests in each pass over the weights" (`guide/performance.md:6`) — the batch is processed in sub-passes.
- **[SRC]** Overhead: 93.0× stock vLLM prefill per GPU at the highest load tried, 71.4× versus prefill of 24 at once, 20.1× versus decoding at 512 streams — `guide/performance.md:27`.
- **[SRC]** Segmenting: "The prover folds each segment's commitments into one short commitment and carries it into the next segment, so it need not keep the whole trace. A proximity test is run on the last short commitment." — `docs/protocol.md:161`. **[PAPER]** per segment g > 0: Code switch (with κ_req proof-of-work bits) "from the group of segment g − 1 to a message that also holds the cells of segment g and the lower segments' cells that higher segments read"; then lookup, own rounds, range test, batching, Fold — paper.txt:4643-4656. Segments "are not proofs of their own: one proof runs through all of them in order" (paper.txt:4928-4929).
- **[SRC]** Inter-segment carried data: `qa` (q, k, v, o) from the feed-forward segment to its attention segment; `xbO` (the residual stream, 5 limbs × d per token) to the next group — `docs/format/11-2-feed-forward-segment.md:57-63`. A segment that reads an earlier segment's matrix runs its own range test on it again with fresh Θ (`11-1-machinery.md:1298-1300`).
- **[SRC]** The weight tables "are not stored: in each batch, `cp_prove` recomputes the parts it needs from the model's weight files and compares them with the stored level" of the hash tree — `docs/protocol.md:74`; `docs/model.md:497-504`.
- **[SRC]** Prover source layout: `prover/field/lazy_gl64.cuh`, `lazy_signed.cuh` ("arithmetic with delayed reduction for kernels' inner loops; the encoders' fast transform", `prover/README.md:61`), `prover/engine/{encode,fold,products,lkp_pieces,tree,tiled}.cuh`, `prover/attn/*`, `prover/hash_commitment/*`; pinned to CUDA 13.2 on x86-64 with SHA extensions (README.md:63-69). "Every row adds bytes to each column that a proof opens, and time to the encoding of the rows, so fewer rows give a smaller proof and a faster prover" (`prover/docs/layout.md:14`).
- **[REPORT]** "recomputing adds about 1 to 1.5% to the prover's work" (forward pass share; appendix, tr.txt:738); sumchecks are "90-95% of all the interaction rounds" (a round count, not a time share; tr.txt:332-333); each request "waits about five minutes" (tr.txt:647).
- **[SRC]** Batching across requests uses a salted Merkle "batch tree" over per-request chain seals so shared challenges are sampled once; the table is opened once per batch (64 columns) — `docs/protocol.md:169-187`.

### Inferences
- **[INFER]** Volume estimate per 4-layer group at T = 1,024 (from the layout formulas and `policy.txt`): feed-forward segment ≈ 1.2·10^9 byte cells in `af` alone (≈ 4·10^8 packed elements) plus ≈ 1.3·10^8 range-test digit elements and ≈ 2^30 lookup key slots; attention segment ≈ 5 × 20 × (2^22 + 2^19) ≈ 4.7·10^8 cells (≈ 1.6·10^8 packed elements) and ≈ 2^29 key slots. So even at T = 1,024 the feed-forward trace is larger than the attention trace; attention overtakes at longer contexts (quadratic).
- **[INFER]** The scaling of rate with batch size (17 → 111 → 123 tokens/s) shows a large per-batch fixed cost: the pass over all 400 billion weights for the shared table test and weight-claim folding ("Each request's proof also does work over all 400.7 billion committed weights, once per request" — paper.txt:2535-2537 — while the table opening is once per batch). The marginal request at batch 24–64 costs ≈ 7–8 s.
- **[INFER]** Since no profile is published, the claim "encoding and hashing small integers on a GPU is cheap" in research-directions §7.2 remains an assumption; the only hard evidence is the end-to-end rate.

### Gaps
- No stage-level timing (encode/NTT vs. Merkle hashing vs. sumcheck vs. lookup trees vs. weight streaming) in any source read: README, `guide/performance.md`, `docs/results.md` (not opened; 3.7 kB), `docs/architecture.md` (grep only), paper §7 and Appendix H (H.2 not read in full), report §6.
- GPU kernels were not read; no claims are made about their techniques beyond file names and the README one-liners.

## 8. Known optimizations the authors say they left out

### Takeaway
The only explicit statement is one generic sentence in the technical report; neither the repo nor the paper enumerates the omitted optimizations.

### Cited Findings
- **[REPORT]** §7, "Protocol": "There are meaningful optimizations that we did not incorporate in the cryptographic protocol underlying FlashProve. These include optimizations in prover time, prover memory, argument size, and verifier time that would result from a more careful application of the IOP and zkML toolkits as well as fine-tuning the hash-based compilation." (tr.txt:665-668; also the introduction, tr.txt:64).
- **[REPORT]** §7, "Approximate range checks": imperfect completeness; retry with a different source of randomness "in a future release" (tr.txt:553-559).
- **[SRC]** Places where the release visibly leaves room: no proof of work on the range-test round (`work smallness 0 0 0`, `policy.txt:12`); proof size is dominated by openings at rate-1/2 first stages with 219 positions (section 1); a matrix read by two segments is range-tested twice (`11-1-machinery.md:1298-1300`); the head computes margins for all 1,024 positions even when one token is checked (`11-4`); the source "has room for vectors U1 and U2" but uses only U3 and J = 1 packed rows per array row (`11-1-machinery.md:1115-1127`); context limited to T ≤ 1,024 (`docs/model.md:218-221`).
- **[PAPER]** Open problems listed are all about proofs (extraction for the released committer, completeness beyond served requests, zero knowledge for batches, many proofs, adaptive configuration), not performance — paper.txt:2711-2746.

### Inferences
- **[INFER]** Candidates the design itself suggests but does not use: skipping committed argmax bits in favour of a one-hot; per-position head work only at checked positions; sharing one range test across segments for carried matrices; recursion/aggregation for proof size (18.78 MB is opening-dominated).

### Gaps

## 9. Ranked techniques transferable to jolt-atlas, with what each would replace

### Takeaway
Ranked by expected reduction of committed one-hot digits per element at the smallest architectural change: (1) approximate no-overflow check by shared random projections for linearly-consumed tensors; (2) partial-function semantics so that check is sufficient; (3) fused (range + clamp + function) tables on scaled virtual keys; (4) FlashProve-style attention; (5) two-sided scaled-key range checks for non-digit-aligned bounds; (6) byte-limb dense commitment with lane packing, if a hash-based commitment is ever adopted; (7) bit-plane multiplicities / grand-product lookups on virtual keys; (8) public-map absorption into weight claims; (9) segment folding with carried boundary tensors.

### Cited Findings
- The constructions referenced here are documented in sections 2–5 above: random-projection range test (`blocks/iop/rng.h:6-25, 332-397`; `docs/format/11-1-machinery.md:1025-1300`), partial-function model with range conditions (`docs/model.md:292-317`), scaled keys SK/HK and fused tables (`docs/format/11-2-feed-forward-segment.md:604-636`; `11-1-machinery.md:316-334`), attention (`docs/format/11-3-attention-segment.md:302-457`), two-sided remainders (`11-3:398-399, 434-435`; `11-2:557-571`), packing (`11-1-machinery.md:1109-1116`), lookup with bit-plane multiplicities (`11-1-machinery.md:126-200`), RoPE in the weight claim (`11-2:854-863`), segment carry (`docs/protocol.md:161`).
- jolt-atlas baseline numbers are from `/Users/kg/swe/icme/official/jolt-atlas/docs/optimization-roadmap.md` §1 (12 digits per einsum output, 8 per Add/Sub/Sum clamp, 34 per attention pair, 25.2 s of 40.6 s in commitment on GPT-2).

### Inferences
All items below are my assessment.

1. **Shared random-projection no-overflow check (replaces the 8 output-range/clamp digits on einsum outputs and on Add/Sub/Sum).** Draw Θ ∈ {0, ±1}^(k×128) from the transcript after the tensor is fixed; commit only the digits of the 128 combinations per row; tie them to the virtual tensor with one sumcheck over the column axis ending in an ordinary MLE claim; the verifier evaluates Θ's extension in O(128·k). Digits per row ≈ 128 × ⌈(33 + ½·log2(128k))/4⌉ instead of 8k: ≈ 6× fewer at k = 1024, ≈ 20× at k = 4096; a loss below k ≈ 176 (keep exact digits there). Imperfect completeness ≤ 2e^−128 per combination at the stated window. Requires item 2. Soundness needs the "fixed before Θ" ordering and inherits the 2^−128-per-round versus 113-bit-union-bound question FlashProve documents; with 128-bit challenges and no grinding, budget the union bound explicitly. Supersedes roadmap D2 and most of D1 for these digits; answers research-directions §9 step 7.
2. **Partial-function semantics for linearly-consumed values (enables 1; replaces "saturating clamp everywhere").** FlashProve defines the model only where values stay in declared intervals and proves nothing otherwise; clamps exist only as explicit table lookups in front of non-linear consumers. For jolt-atlas this is a `SemVersion` change: outputs consumed only by linear ops become "unclamped, proof fails on overflow", with a compile-time worst-case bound (as `cp_commit` does) to show real models never hit it.
3. **Fused tables on scaled virtual keys (replaces clamp-then-lookup double decompositions; roadmap B2, B3, C2, C4).** One table row = input + 2^a·output (+ flags); one key built as a linear form. In one-hot terms: the activation's address digits double as the range proof of the wide value, and the table output is read from the same address. FlashProve shows the full menu: clamp, SiLU, sigmoid, exp-with-cutoff-and-mask.
4. **Attention as in FlashProve (confirms roadmap C3 and settles two of its open questions).** Unrescaled virtual scores; committed argmax; one fused lookup on max − score with a coarse shift (sh = 8) so the address is ≈ 16 bits rather than "40+": FlashProve keeps the address small by (i) 12-bit clamped q, k so |score| ≤ 128·2047², and (ii) a table whose high rows absorb everything beyond the cutoff in steps of ρ with a 16-bit remainder. Normalization inside the ·V division with a two-sided remainder. Target: per pair one ≈ 16-bit address (4 four-bit digits + a few for the remainder) instead of 34 digits.
5. **Two-sided and scaled-key range checks (replaces read-raf comparisons; roadmap B1).** For a bound B that is not a power of the digit base, check both R and B − 1 − R (attention `rh`/`rhp`; norm `rr`/`rq`, `l1`/`h1`), or multiply the key by 2^(w − k) so a w-bit table enforces a k-bit range (SK/HK, `mul_j`). The isqrt/reciprocal construction is exactly B1's slack-pair relation, done per row.
6. **Remainder low bits as a lookup on a virtual key (would replace the 4 remainder digits).** FlashProve commits nothing for the low 16 bits of a remainder because its grand-product lookup accepts virtual keys. With Shout one-hot addresses this is not available; it becomes available with a multiplicity-based range check (roadmap D4). FlashProve's version: multiplicities as 32 bit-planes per table row (tiny commitment, bit-ness sumcheck), product trees by GKR. Over Fp128 the instance-size soundness loss must be handled (FlashProve relies on a 192-bit challenge field).
7. **Byte-limb dense commitment with lane packing (relevant only to "strategy A", a hash-based trace commitment; research-directions §5 "fourth option", §9 step 8).** Signed-byte cells, 3 per 64-bit element at radix 2^20, with the random-projection check doubling as the unpacking-consistency proof via committed partial sums ("reads"). Concrete parameters to benchmark against Akita one-hot digits: Goldilocks, rate-1/2 first stage, 219 queries, Johnson regime, 20-bit grinding, BLAKE2b.
8. **Absorb public linear maps into the verifier-side factor of a matmul claim (replaces committed/virtualized intermediate nodes).** RoPE is applied inside the weight claim's factor; the embedding gather is a claim with a public sparse vector. Analogues: roadmap B4 importer fusions (MoveAxis into einsum strings), bias/residual fusion C1.
9. **Segment folding with carried boundary tensors (memory-bounded proving; research-directions §4.5, §8).** One proof through all segments, each closed segment folded to a short commitment; only boundary tensors (residual stream, q/k/v/o) are re-sent. In a multilinear system the analogue is carrying only boundary evaluation claims and dropping each layer's witness after its opening reduction.
10. **Mixture-of-experts via indicator vectors and selector-weighted weight claims.** Directly reusable if jolt-atlas ever proves conditional subgraphs; not relevant to current zoo models.

Lower-value or non-transferable: the zero-knowledge machinery (masked sumchecks, opening budgets, link proofs, batch tree), which exists for weight hiding; float64-generated tables pinned by digest (jolt-atlas's integer-only table generation is stricter).

### Gaps
- None of these has been prototyped or measured in jolt-atlas; digit-count estimates are counting arguments in the style of the roadmap.
- The interaction of item 1 with jolt-atlas's fused rebase (interior/saturated split, bucket packing) was not analysed against the code, by instruction (no jolt-atlas code review in scope).
- Whether Akita's commitment cost for the 128-per-row combination digits has the same per-digit cost as today's digits (they are dense along a new axis) needs the roadmap's digit census.
