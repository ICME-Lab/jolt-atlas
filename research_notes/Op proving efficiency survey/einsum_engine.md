# Einsum (matmul / tensor contraction) proving engine: can it be made faster?

Conventions used in these notes:

- **[CODE]** = fact read in the working tree on branch `dev` (2026-11-09), cited as `path:line` or `path` + function name. No cargo command was run; nothing was measured in this session.
- **[LIT]** = claim from a paper / web page, cited by URL.
- **[MEMO]** = measurement recorded in the repo owner's session memory notes (`/Users/kg/.claude/projects/-Users-kg-swe-icme-official-jolt-atlas/memory/*.md`). These are historical (Aug–Oct 2026, several on the retired BN254/Dory backend), were not re-measured, and are flagged wherever used.
- **[EST]** = my own estimate / inference. Not measured.

Paths are relative to `/Users/kg/swe/icme/official/jolt-atlas/`.

Headline (details below): the contraction sumcheck is already the Thaler'13 protocol with the minimum number of rounds for every supported pattern; the sumcheck rounds themselves are tiny. The costs that matter for an einsum node are (1) the O(input size) operand **fold** before the sumcheck and (2) the **fused rescale + clamp**, which commits about 12 one-hot digits per output element and is paid in the PCS commit phase, which is 25.2 s of the 40.6 s GPT-2 proof per the README. The biggest available wins are therefore on the rescale/clamp side (fewer committed digits per output, fusing the bias `Add`), not in the dot-product sumcheck.

## 1. Is the matmul sumcheck Thaler'13-style? Rounds per pattern versus the minimum

### Takeaway
Yes. Every supported einsum is proven as `acc(r0) = Σ_h L(h)·R(h)·EQ(h)` after folding both operands at the output point, summing only over the contracted index (plus the shared batch index for batched matmul). Round counts equal the information-theoretic minimum for all three layouts; the only excess is in per-round *work* for the batched layout (degree-3 messages computed densely, no Gruen/split-eq).

### Cited Findings
- [CODE] The relation is `ContractionRelation`: input claim `q(r0)·2^S + rem(r0)` (fused) or `out(r0)` (not fused), output claim `L(ρ_L)·R(ρ_R)·EQ`. `jolt-atlas-verifier/src/onnx_proof/ops/einsum/mod.rs:112-131` (doc comment), `:188-196` (`input_expression`, `output_expression`).
- [CODE] `rounds()` and `degree()` come from the layout geometry: `mod.rs:180-186`. Degree is 2 with no EQ factor, 3 with one: `jolt-atlas-verifier/src/onnx_proof/ops/einsum/dot.rs` `EqSchedule::degree`.
- [CODE] The importer emits only four canonical equations, `["mk,kn->mn", "mk,nk->mn", "amk,ank->amn", "abmk,abnk->abmn"]`: `atlas-onnx-import/src/lower.rs:25`, gate at `:402-406`. They map to three layouts: `jolt-atlas-verifier/src/utils/dims.rs` `EINSUM_REGISTRY` (and the comment block in `einsum/mod.rs:48-54`).
- [CODE] Per-pattern rounds, degree, and minimum:

| Canonical equation | Layout | Rounds (code) | Degree | Minimum rounds | Notes |
|---|---|---|---|---|---|
| `mk,kn->mn` | `MkKnMnLayout` | `log k` (`mk_kn_mn.rs:39-41`) | 2 (`EqSchedule::None`, `:43-45`) | `log k` | Exactly Thaler'13: `C(r_m,r_n) = Σ_k A(r_m,k)·B(k,r_n)` |
| `mk,nk->mn` | `KNkNLayout` (`k,nk->n`) | `log k` (`k_nk_n.rs:38-40`) | 2 | `log k` | Only provable with `m == 1`; dispatch asserts (`utils/dims.rs` `extract_k_nk_n_dims`). Left operand is the raw i32 vector, not folded (`k_nk_n.rs:66`) |
| `amk,ank->amn` | `AbmkAbnkAbmnLayout`, batch pack `(1,a)` | `log a + log k` | 3 | `log a + log k` | See next row |
| `abmk,abnk->abmn` | `AbmkAbnkAbmnLayout` | `log(ab) + log k` (`abmk_abnk_abmn.rs:65-67`) | 3 (`EqSchedule::High`, `:69-74`) | `log(ab) + log k` | Both operands carry the batch index, so the batch cube must be summed (it is a Hadamard product in the batch index): `out(r_ab,r_m,r_n) = Σ_{h,j} eq(r_ab,h)·L(h,r_m,j)·R(h,r_n,j)` |

- [CODE] Operand opening points after the sumcheck: `mk,kn->mn` → left `(r_m ‖ r_k)`, right `(r_k ‖ r_n)` (`mk_kn_mn.rs:83-92`); `k,nk->n` → left `r_k`, right `(r_n ‖ r_k)` (`k_nk_n.rs:72-80`); batched → left `(r_ab ‖ r_m ‖ r_k)`, right `(r_ab ‖ r_n ‖ r_k)` (`abmk_abnk_abmn.rs:130-141`).
- [CODE] The prover (`EinsumDotProver`) folds first, then runs the rounds over tables of size `k` (or `ab·k`): `jolt-atlas-core/src/onnx_proof/ops/einsum/dot.rs`, `initialize` and `round_message`.
- [CODE] Fold cost is linear in operand size: e.g. `mk_kn_mn.rs:58-75` does `m·k` + `k·n` `eq.mul_i64(operand as i64)` multiply-adds; `abmk_abnk_abmn.rs:95-122` does `ab·m·k` + `ab·n·k`.
- [LIT] Thaler's matmul protocol is a special-purpose sumcheck "of interest in its own right"; the paper reports a prover less than 10x slower than a C++ program that just evaluates the circuit, across its experiments — [Thaler, ePrint 2013/351](https://eprint.iacr.org/2013/351).
- [LIT] zkLLM uses the same protocol, citing Thaler 2013 and Ghodsi et al. 2017, with prover time `O(mn+np)` — [zkLLM, arXiv 2404.16109](https://arxiv.org/html/2404.16109v1).
- [LIT] zkGPT also uses Thaler's matmul protocol, calls its `O(nm+mk)` complexity optimal, and says the time "is dominated by computing the bookkeeping table for the input matrices A and B" (i.e. the fold) — [zkGPT, USENIX Security 2025](https://home.cse.ust.hk/~kaichen/papers/zkgpt-security25.pdf).

### Inferences
- [EST] There is no asymptotic slack in the contraction protocol. Prover work per node is `O(|L| + |R|)` small-scalar multiplications for the fold plus `O(k)` (or `O(ab·k)`) field multiplications for the rounds. For a weight matmul such as GPT-2's 768×3072 MLP projection the fold touches ~2.4M (4.2M padded) weights while the sumcheck runs over a table of 1024 entries, so the fold is >99.9% of the node's arithmetic.
- [EST] `mk,nk->mn` with `m > 1` is not provable today (it panics at dispatch). That is a coverage limitation, not a speed issue; a general `mk,nk->mn` layout would be a fourth trivial layout (fold left over `m`, right over `n`, both indexed by `k`).

### Gaps
- No per-op timing for einsum on the current Fp128 + Akita build exists in `docs/`, `specs/`, `README.md`, or any bench target (there is no `benches/` directory). The only current numbers are whole-stage (Section 3).

## 2. Binding order, split-eq / Gruen, small-value and unreduced arithmetic in the dot engine

### Takeaway
The dot engine is the plainest possible implementation: dense tables, `HighToLow` binding, fully reduced field arithmetic in every inner loop, and a materialized dense eq table for the batched layout. It uses none of the split-eq / Gruen / delayed-reduction machinery that other provers in the same repo use. The only small-value use is `mul_i64` in the fold. This costs little in absolute terms for 2-D matmul (tables of size `k`), and about 2–3x in the round kernel for batched matmul.

### Cited Findings
- [CODE] All three schedules bind `HighToLow` via `bind_parallel(r_j, BindingOrder::HighToLow)` on `left`, `right` and (when present) `eq`: `jolt-atlas-core/src/onnx_proof/ops/einsum/dot.rs`, `fn bind`.
- [CODE] `EqSchedule::None` round: per pair, `sumcheck_evals(i, 2, HighToLow)` on both operands (the trait method returns a `Vec<F>`, i.e. a heap allocation per index per operand per round) then two reduced field products, summed with reduced additions under rayon `reduce`: `dot.rs`, `round_message`, first match arm. `sumcheck_evals` signature returning `Vec<F>`: `atlas-algebra/src/poly/multilinear_polynomial.rs:725`.
- [CODE] `EqSchedule::High` round (batched matmul): three evaluation points, each `l·r·e` = 2 reduced field multiplications, so 6 multiplications per pair per round. After the eq cube is fully bound (rounds ≥ `log_eq`) the code still multiplies every term by the cached scalar `eq_bound_claim` and still sends a degree-3 message: `dot.rs`, `round_message`, `EqSchedule::High` arm.
- [CODE] The batch eq is a dense table `MultilinearPolynomial::from(eq_r_ab)`: `jolt-atlas-verifier/src/onnx_proof/ops/einsum/abmk_abnk_abmn.rs:126`.
- [CODE] `EqSchedule::Low` exists in the engine but no current layout returns it (the three layouts return `None`, `None`, `High`): `mk_kn_mn.rs:43-45`, `k_nk_n.rs:42-44`, `abmk_abnk_abmn.rs:69-74`. It is dead code on the current canonical set.
- [CODE] Small-value use in the fold: `eq_r_m[i].mul_i64(left_operand[i*k+j] as i64)` summed with reduced `.sum()`: `mk_kn_mn.rs:58-75`, `k_nk_n.rs:56-64`, `abmk_abnk_abmn.rs:95-122`. `mul_i64` forwards to the Solinas `Ring::mul_i64`: `atlas-algebra/src/field/fp128.rs:377`.
- [CODE] The repo already has the tools the dot engine does not use: a delayed-reduction ladder on `JoltField` (`mul_u64_unreduced`, `UnreducedMulU64` accumulators, `mul_to_product_accum`): `atlas-algebra/src/field/mod.rs:180-288`; and `SplitEqUnreducedFold` with `par_fold_out_in_unreduced` / `gruen_round_deg_3` over upstream `GruenSplitEqPolynomial`: `atlas-algebra/src/poly/split_eq_poly.rs:51-80`.
- [CODE] `GruenSplitEqPolynomial` / `SplitEqUnreducedFold` are used by softmax (`ops/softmax_last_axis/{exp_sum,recip_mult,max,exponentiation/mult}.rs`), the generic relation engine (`jolt-atlas-core/src/onnx_proof/relation.rs`) and the atlas-sumcheck subprotocols (booleanity, ps_shout, ra_virtual, identity range check, opening reduction), but not by `ops/einsum/dot.rs` (grep for both identifiers, this session).
- [CODE] Fold memory access: in `MkKnMnLayout::fold` the left fold reads `left_operand[i*k + j]` with `j` in the outer (parallel) loop and `i` in the inner loop, i.e. stride `k` (`mk_kn_mn.rs:58-66`); `KNkNLayout::fold` reads the weight matrix as `right_operand[h*k + j]` with `h` inner, stride `k` (`k_nk_n.rs:56-64`); the batched layout reads `(h*m+i)*k + j` with `i` inner (`abmk_abnk_abmn.rs:95-122`). Only the right fold of `mk,kn->mn` (`right_operand[j*n + h]`, `mk_kn_mn.rs:67-75`) walks memory contiguously.
- [CODE] `KNkNLayout::fold` clones the left operand tensor into a compact i32 polynomial (`MultilinearPolynomial::from(left_operand.clone())`, `k_nk_n.rs:66`); it is a `k`-element copy, negligible.
- [CODE] `bind_parallel` for dense polys is in-place for `HighToLow` with a `filter(a != b)` branch: `atlas-algebra/src/poly/dense_mlpoly.rs` `bound_poly_var_top_zero_optimized`.
- [CODE] The fused intermediates (`quotient`, `remainder`) are read from the trace cache, not recomputed, but each use calls `padded_pow2()`, which copies: `jolt-atlas-core/src/onnx_proof/fused_rebase.rs:139-149`, `:164-175`.

The current `dev` tree does not contain that: `dot.rs` is `HighToLow` with a dense `Folded.eq`. Source: memory note `softmax-phase1-eq-hoist.md`. So that optimization was lost or never landed across the tracer rewrite / relation migration.

The earlier version reports consistent 2–3x on Spartan's first sumcheck — [ePrint 2025/1117](https://eprint.iacr.org/2025/1117).
- [CODE] `docs/upstream-inventory.md` records that upstream `jolt-sumcheck` has `prove_uniskip_*` / `CenteredIntegerDomain` (univariate skip) and that the atlas copy "had no callers and is deleted"; operand polynomials stay atlas-owned because their 125-bit-challenge binding is "about a quarter faster per bind than `jolt-poly`'s" (2^22 evaluations: ~11 ms vs ~15 ms).

### Inferences
- [EST] The small-value sumcheck (Bagad–Domb–Thaler / 2026/587) does **not** apply to the contraction rounds as structured: after the Thaler fold, `L` and `R` are random-looking full-width field elements, so no round sees small values. The place where the i32 structure can be exploited is the fold, and the code already does so with `mul_i64`. What is missing there is delayed reduction: accumulate `Σ_i eq[i]·w[i]` as unreduced `field × u64` products (`mul_u64_unreduced` into an `UnreducedMulU64`-accumulating type, signs handled by two accumulators or an offset) and reduce once per output coefficient. With mul_u64 ≈ 3.4 ns and add ≈ 1.6 ns [MEMO], I estimate 1.5–2.5x on the fold's arithmetic.
- [EST] Loop interchange / cache: for a weight matrix stored `[n, k]` (the `k,nk->n` case, which is every transposed-weight `Gemm`), the fold currently walks a column per output coefficient, touching `n` cache lines `k·4` bytes apart. Rewriting as row-major AXPY (`acc[j] += eq[h]·W[h][j]`, per-thread unreduced accumulators over row blocks, then merge) makes access sequential and SIMD-friendly. Likely another 1.5–3x on large weights where the matrix exceeds L2 (GPT-2 3072×768 i32 = 9.4 MB). The two effects multiply only partly; a combined 2–4x on fold time is my estimate.
- [EST] For the batched layout, using `GruenSplitEqPolynomial` for the `log(ab)` eq rounds and sending a degree-2 message (scaled by the bound eq scalar) for the remaining `log k` rounds cuts multiplications per pair from 6 to about 2–3 (2–3x on those rounds). Sending a lower-degree message than the declared bound is fine for the verifier only if the wire format still carries degree-3 polynomials, so either keep the degree-3 encoding (prover computes `s(X) = eq_scalar·q(X)` with `q` quadratic, cheaply) or make it a protocol change. The first option is transcript-identical and needs no verifier change.
- [EST] The `Vec<F>` allocation in `sumcheck_evals(i, 2, ..)` in the degree-2 arm is avoidable by using `sumcheck_evals_array::<2>` as the degree-3 arms already do. Tiny absolute win (tables of size `k`), but free.
- [EST] Univariate skip is not useful here: it removes rounds from sumchecks whose first rounds are over small values with high degree; the contraction has degree 2–3 and full-field tables.

### Gaps
- I could not run anything, so the split between fold time and round time on the current build is unknown. A `--trace-terminal` run of `models/gpt2` already instruments `EinsumDotProver::initialize` and `Einsum::prove` with tracing spans (both carry `#[tracing::instrument]`), so one run would settle it.
- Whether `Ring::mul_i64` on the vendored Solinas field already does a cheap partial reduction (which would shrink the delayed-reduction gain) was not checked in `third_party/jolt-field/src/solinas/`.

## 3. Fused rescale + clamp after the dot product: what is committed, how it is proven, and its cost relative to the dot product

### Takeaway
Per non-scalar fused einsum output element the prover commits one-hot digits for a 32-bit output range check (8 four-bit chunks) and an `S`-bit remainder range check (4 chunks at the default scale 14), plus saturation-slack chunks that are empty unless something saturates: about 12 hot entries per element. Both checks are already deferred and batched model-wide into packed buckets, with no per-node lookup sumcheck and no RaVirtual. This commitment work, not the contraction sumcheck, is where an einsum node's cost sits, because the PCS commit stage is ~62% of GPT-2 prove time.

### Cited Findings
- [CODE] Protocol skeleton: `acc(r) = rescaled(r)·2^S + R(r)`; `output = SatClamp(rescaled)`; `R ∈ [0, 2^S)`: `jolt-atlas-verifier/src/onnx_proof/fused_rebase.rs:1-22`. Rebase width: einsum `S = scale`; Mul/Square `S`; Cube `2S`: `:62-71`. Default scale is 14: `atlas-onnx-import/src/lib.rs:52`, `atlas-trace/src/model.rs:241`.
- [CODE] `Einsum::prove` order: `fused_rebase::prove_pre` (append remainder advice opening at `r0`, register clamp job), contraction sumcheck, `prove_remainder_rc` (register remainder job): `jolt-atlas-core/src/onnx_proof/ops/einsum/mod.rs` `ProveOp for Einsum`.
- [CODE] `rescaled` (`VirtualPoly::ClampAcc`) and `R` (`VirtualPoly::RescaleRemainder`) are virtual advice openings at the node's output point; the quotient and remainder tensors themselves are not committed as dense columns. `fused_rebase.rs:103-116` (verifier), `jolt-atlas-core/src/onnx_proof/fused_rebase.rs:110-120` (prover evaluates `remainder.evaluate_mle(&r0.r)`).
- [CODE] Per-node committed polynomials for einsum are empty; everything is committed per packed bucket at model level: `fused_rebase.rs:137-142`, `global_clamp.rs:242-248` (`bucket_committed_polys`).
- [CODE] Bucketing: nodes are grouped by width and packed first-fit-decreasing into buckets whose capacity is the largest clamped node; each node occupies an aligned power-of-two segment; a bucket sumcheck uses cycle weight `Σ_n γ_n·eq(r_n, t − off_n)`: `global_clamp.rs:1-18`, `:113-160`.
- [CODE] Clamp via the interior/saturated split: per bucket cycle, `OUT = out + 2^31` in 8 dense 4-bit chunks; `IND` virtual (Hamming weight of slack chunks); `S = IND·|acc − out|` in `w/4` sparse chunks, `w ∈ {40,48,56,64}`; one degree-4 split sumcheck per bucket and a Booleanity sumcheck with a linear term tying chunk values and Hamming weights; no RaVirtual: `jolt-atlas-verifier/src/onnx_proof/clamp_split.rs:1-56`. `LOG_K_CHUNK = 4`: `common/src/consts/general.rs:2`. `OUT_LOG_K = 32`: `clamp_split.rs` (constant).
- [CODE] Per-bucket "exact" mode: the prover declares (public claim) that a bucket has no saturated element; then only a value sumcheck on `OUT` plus Booleanity on the 8 OUT chunks runs, the verifier checks `acc = out` per node, and slack chunks are empty/unopened: `jolt-atlas-core/src/onnx_proof/deferred_lookups.rs` `prove_all` (the `exact` vector and `Params::Exact` branch). Public unsaturated model outputs skip the clamp entirely (`exact_output_verifier`): `clamp_split.rs:165-178`.
- [CODE] Clamp width is static per node from `clamp_bound`; for einsum, `einsum_acc_bound >> scale`, using constant-operand row sums when one operand is a constant, else `2^62 · contracted size`: `atlas-trace/src/op/einsum.rs:278-280`, `:292-320`; widths `W40/W48/W56/W64`: `atlas-trace/src/model.rs:251-284`.
- [CODE] Remainder range check: buckets keyed by rebase width; value sumcheck + Booleanity with chunk-value linear term; committed chunks `ceil(width / 4)`: `global_clamp.rs:86-111`, `:164-168`; `deferred_lookups.rs` `prove_all`, "Rescale-remainder range checks" block. At `S = 14` that is 4 chunks; Cube (`2S = 28`) 7 chunks.
- [CODE] Scalar outputs open `rescaled` and `R` in the clear and are checked directly by the verifier: `fused_rebase.rs:158-182`, `:197-214`.
- [CODE] All these lookups are deferred out of the node loop and proven as a handful of batched sumchecks (`DeferredClampSplit`, `DeferredClampChunkChecks`, `DeferredRemainderRC`, `DeferredRemainderRaChecks`) via `prove_relation_batch_parallel`: `jolt-atlas-core/src/onnx_proof/deferred_lookups.rs` module doc and `prove_all`.
- [CODE] Current whole-proof timings (README, GPT-2, MacBook Pro M3 16 GB, Akita over Fp128): witness + commitment 25.2 s; IOP 5.28 s; opening reduction + Akita openings 6.72 s; total 40.6 s traced, 39.9 s median untraced; verify 2.17–2.21 s; proof 2.42 MiB: `README.md:59-80`.
- [MEMO] Akita one-hot commit cost on the M3 was ~90 ns per hot entry, and ~45% of committed one-hot entries were zero digits (Qwen census). GPT-2 commit time was "dominated by two 2^24 one-hot groups ~10 s each". Sources: memory notes `lattice-akita-cutover.md`, `upstream-adoption.md`. Not re-measured.
- [MEMO] On Qwen every clamp bucket had zero saturated elements, so every bucket ran in exact mode. Source: `qwen-sub-minute-brainstorm.md`.
- [MEMO] A LogUp-GKR range check was built and measured as a net regression on BN254 (46.3 → 55.4 s), attributed to ~30–60 field multiplications per element versus the tuned one-hot Booleanity; the note says "LogUp only pays on small fields". Source: `qwen-sub-minute-brainstorm.md`. This was on a 254-bit field with Dory; it has not been re-evaluated on Fp128 + Akita.
- [LIT] zkLLM proves rescaling the same way: `Z = γZ' + R` with the remainder checked by a lookup (tlookup), batched by random linear combination — [zkLLM, arXiv 2404.16109](https://arxiv.org/html/2404.16109v1).
- [LIT] zkGPT: "proving range relations is the bottleneck in our system, as it is more costly than proving arithmetic relations"; its GPT-2 breakdown (32 threads, all optimizations) is commit advice 0.8 s, GKR layer sumcheck 5.7 s, combine sumcheck 3.2 s, lookup 12.1 s, total 21.8 s — [zkGPT, Table 5](https://home.cse.ust.hk/~kaichen/papers/zkgpt-security25.pdf).

### Inferences
- [EST] Per fused einsum output element: 8 (OUT) + 4 (remainder) = 12 committed hot one-hot entries (slack chunks empty when unsaturated). At ~90 ns per hot entry [MEMO] that is roughly 1.1 µs of commit time per output element, before the Booleanity/value sumchecks and the opening reduction. By comparison the contraction costs one `mul_i64` (~3.4 ns [MEMO]) per *input* element and a few ns per contracted index. For a layer whose output is not much smaller than its weight matrix divided by ~300, rescale/clamp dominates; for a short-sequence weight matmul (GPT-2 at sequence length 16: 16×3072 outputs vs 768×3072 weights, ratio 1:768) the fold and the rebase commits are the same order of magnitude (≈50k·1.1 µs ≈ 55 ms commit vs ≈2.4M·3.4 ns ≈ 8 ms single-threaded fold). So at short sequence lengths neither is large per node, and at long sequence lengths the rebase commits dominate by a wide margin.
- [EST] Can the remainder range check and the saturating clamp be merged into one lookup? They are already both plain digit range checks (value sumcheck + Booleanity). Merging them into one 46-bit decomposition gives `ceil(46/4) = 12` chunks, the same as 8 + 4, so there is no commit saving at 4-bit chunks; the saving would be IOP-only (one bucket family, one value sumcheck, one fewer advice opening per node). Since the IOP is 5.28 s of 40.6 s, this is a low-single-digit-percent item.
- [EST] Are they batched across all nodes? Yes, already (one bucket family per width, model-wide). There is no further cross-node batching win of that kind.
- [EST] What *would* cut commits: (a) not committing digits that are provably or declaredly constant. With the offset encoding `OUT = out + 2^31` the top chunks of small values are `0x7…`/`0x8…`, never identically zero, so the PCS adapter's zero-class skip cannot fire. A per-bucket prover-declared narrow width `b` (public claim, like the existing exact flag), with `OUT_b = out + 2^(b−1)` in `ceil(b/4)` chunks, is sound for the same reason the exact flag is: a narrower range check is strictly stronger than `out ∈ i32`, and it implies no saturation. Completeness depends on the data; the prover picks `b` from the trace. If activations at scale 2^14 stay below 2^23 in magnitude (|x| < 512 in real terms), 8 chunks become 6 (−25% of clamp digits; −17% of the 12). (b) Fusing the bias add, next item.
- [EST] Rescale deferral across consecutive linear ops: `Gemm`/`MatMul + Add(bias)` currently lowers to an `Einsum` node followed by a separate `Add` node (`atlas-onnx-import/src/passes.rs:763-957`, bias `Add` emitted at `:941-957`), and `Add` carries its own saturating clamp (8 OUT chunks; `clamp_lookups/mod.rs:1-20` lists `Add`/`Sub`/`Sum`). Fusing the bias into the einsum accumulator, `acc' = Σ L·R + b·2^S`, gives `floor(acc'/2^S) = floor(acc/2^S) + b` exactly (the added term is a multiple of the divisor), so quotient/remainder semantics are unchanged and the only behavioral difference is `SatClamp(SatClamp(q) + b)` versus `SatClamp(q + b)`, which differ only when the intermediate saturates. On the proving side the bias is a public constant folded into the relation's input claim (`+ 2^S·b(r0)`, verifier evaluates the bias MLE, `O(n)`), and one whole clamped node disappears per linear layer: 20 hot entries per output element (12 + 8) become 12, i.e. −40% of that layer's rebase/clamp commits, plus one fewer node in the IOP. The same fusion applies to a residual `Add` whose other operand is dynamic when the einsum has a single consumer (`acc' = Σ L·R + y·2^S`, with `y(r0)` an extra opening), at the same semantic caveat.
- [EST] This is zkGPT's "constraint fusion" (merge computations between adjacent rounding constraints so fewer range relations are proven); they report a 1.5x overall gain from it on GPT-2 — [zkGPT](https://home.cse.ust.hk/~kaichen/papers/zkgpt-security25.pdf). Their gain is on a system where lookups are 55% of prover time; here commit is ~62%, so a similar order of gain on the affected layers is plausible, but the share of GPT-2's committed digits that belongs to einsum + bias-add nodes is not known (Gap).
- [EST] Wider chunks (8-bit, Akita's K256 family, which upstream ships per [MEMO]) would halve hot entries per element (12 → 6) at the cost of 16x more rows per one-hot column and a heavier Booleanity. On Dory the owner measured chunk-width changes as a wash [MEMO]; on Akita it is untested. This is a PCS-level experiment, not an einsum change.

### Gaps
- What fraction of GPT-2's / Qwen's committed one-hot entries are einsum OUT + remainder chunks versus Add/Mul/activation/softmax chunks. `ATLAS_AKITA_TRACE=1` reportedly prints a per-class census [MEMO], but classes are by arity, not by op; an op-level census needs a small diagnostic.
- Distribution of output magnitudes (needed to size the declared-width proposal). Not available without running the tracer.
- Whether the Akita adapter on `dev` still has the identically-zero-class skip described in the memory notes (not checked in `atlas-pcs/`).

## 4. Batching across einsum nodes; who pays for weight MLE evaluation

### Takeaway
Each einsum node runs its own unbatched contraction sumcheck inside the sequential reverse-topological node loop; only the rescale/clamp lookups are batched model-wide. Weights are public constants, never committed: the verifier evaluates each weight tensor's MLE itself (linear in the tensor), and the prover pays for weights only through the fold. Neither is a prover bottleneck; the weight MLE evaluation is a meaningful share of verifier time.

### Cited Findings
- [CODE] The prover walks nodes sequentially in reverse order, `for node in model.views().iter().rev() { OperatorProver::prove(node, prover) }`: `jolt-atlas-core/src/onnx_proof/prover.rs:179-180`. Each einsum calls `prove_relation` (single instance): `jolt-atlas-core/src/onnx_proof/ops/einsum/mod.rs` `ProveOp for Einsum`.
- [CODE] The contraction's input point is the node's reduced output opening (`accumulator.get_node_output_opening(node.idx)`), which exists only after all consumers have been proven: `jolt-atlas-verifier/src/onnx_proof/ops/einsum/mod.rs:232-243`. Multi-consumer outputs go through a per-node evaluation reduction first: `jolt-atlas-verifier/src/onnx_proof/ops/eval_reduction.rs`.
- [CODE] `Constant` is a zero-round tie whose output claim is derived by the verifier as `value.evaluate_mle(incoming_point)` over the public tensor; it produces no openings and commits nothing (`impl OpLayout for Constant {}`): `jolt-atlas-verifier/src/onnx_proof/ops/constant.rs:28-45`, `:60-120`.
- [CODE] The einsum relation's produced openings are the two operand node outputs (`Target::Input(0)`, `Target::Input(1)`), so a weight operand's claim lands on its `Constant` node and is discharged by that tie: `einsum/mod.rs:199-206`.
- [MEMO] Qwen verify on Fp128 + Mock PCS: 5.75 s total, of which `Constant::verify` 1.3 s. Source: `lattice-akita-cutover.md`.
- [LIT] zkGPT commits to the weights once in preprocessing and reuses the commitment across users; zkLLM commits with Hyrax and reports commit time separately from prover time — [zkGPT](https://home.cse.ust.hk/~kaichen/papers/zkgpt-security25.pdf), [zkLLM](https://arxiv.org/html/2404.16109v1).
- [LIT] zkGPT designs a batched protocol that checks `M` matmuls of the same padded shape in one sumcheck by concatenating matrices and adding `log M` variables (its "circuit squeeze for matrix multiplication"), motivated by thread utilization: small per-layer sumchecks waste time on synchronization. It reports a 1.7x gain on the layer-sumcheck portion from circuit squeeze overall — [zkGPT, Sections 6.2, 7.3](https://home.cse.ust.hk/~kaichen/papers/zkgpt-security25.pdf).

### Inferences
- [EST] Batching contraction sumchecks across nodes is structurally limited here: a node's `r0` depends on its consumers' sumchecks (GKR-style chaining through virtual node outputs), so only nodes with no dependency path between them can share a sumcheck. zkGPT gets around this by committing every intermediate ("advice"), which makes all layers independent; jolt-atlas deliberately keeps node outputs virtual to avoid committing them. Because the contraction rounds are over `log k ≈ 10–12` variables with tables of a few thousand entries, the rounds are far below rayon's useful grain anyway; what batching would save is transcript/proof overhead, not arithmetic. I rate this low value unless profiling shows per-node overhead (span setup, allocation, rayon fan-out for tiny tables) is material.
- [EST] One cheap special case: sibling einsums sharing an operand (Q/K/V projections of the same hidden state, when not already a single fused QKV matmul as the README's tiny-model description suggests for GPT-2) could be proven in one batched sumcheck so the shared operand is opened at points sharing `r_k`, reducing the size of that node's evaluation reduction. Minor.
- [EST] Parallelism: since the fold is embarrassingly parallel and dominates, running the folds of independent einsum nodes concurrently is possible only after their `r0` is known, which is again sequential. The node loop comment in `witness.rs`-adjacent code (`prover.rs:299-311`) records that per-node `par_iter` hurt because it starved the "whale" einsums; inner parallelism is the right call.
- [EST] Weight MLE evaluation is a verifier cost linear in model size (124M `mul_i64`-class operations for GPT-2 per proof, parallelizable). Committing weights instead would make the verifier succinct in the model but would add a dense 2^27-coefficient opening to every proof on the prover side; with Akita commits already the dominant prover stage this is a bad trade for prover speed. It is a product decision (weights public vs private, verifier succinctness), not a speedup.
- [EST] A verifier-side micro-optimization: the weight operand is opened at `(r_n ‖ r_k)` or `(r_k ‖ r_n)`; the verifier's `evaluate_mle` over an i32 tensor can use the same delayed-reduction / split-eq dot product as the prover's fold. It would cut `Constant::verify` by the same 1.5–2.5x factor estimated for the fold.

### Gaps
- Whether the current importer emits one fused QKV einsum or three for GPT-2 / Qwen was not checked (README says the tiny fixtures use a "fused QKV split").
- Current-build verifier breakdown is not documented; the 1.3 s figure is from the Mock-PCS Qwen profile in the memory notes.

## 5. What other zkML systems do for matmul / attention and what they report

### Takeaway
Every sumcheck-based zkML system surveyed uses the same Thaler'13 matmul reduction; the published engineering wins are (1) making the bookkeeping-table (fold) computation cheap by exploiting small quantized values, zero padding and eq-table grouping (zkGPT, 6.5–10x on that step), (2) fusing rounding constraints so fewer range checks are proven (zkGPT, 1.5x overall), and (3) restructuring for parallelism. No surveyed system reports a matmul technique that beats Thaler's protocol asymptotically for dense matrices; Freivalds-style projection is what Thaler's protocol already achieves in the interactive setting.

### Cited Findings
- [LIT] zkGPT matmul: analyzes the classical implementation of Thaler's protocol as costing `2^(⌈log n⌉+⌈log m⌉+1)` field multiplications for the bookkeeping table of an `n×m` matrix; replaces it with (i) grouping `eq(r,b) = eq(x,L)·eq(y,R)`, (ii) skipping zero (padding) entries, (iii) precomputing the `2^Q + 1` possible multiples of each `eq(y,·)` so the inner loop is field additions only (`Q = 16`). For GPT-2's 3072×768 matrix: 8.4×10^6 multiplications + 4.2×10^6 additions classically versus ≈4.5×10^6 additions; estimated 10.2x fewer field-operation-equivalents. Measured single-thread: (32×768)·(768×3072) 0.25 s → 0.037 s; all GPT-2 matmuls 9.8 s → 1.5 s (6.5x) — [zkGPT, Section 4.2 and Table 2](https://home.cse.ust.hk/~kaichen/papers/zkgpt-security25.pdf).
- [LIT] zkGPT end to end: GPT-2 in 21.8 s with 32 threads on a 16-core Xeon 6126 (200 GB RAM), verifier 0.35 s, proof 101 KB; 319.6 s single-threaded without optimizations; Hyrax over BN254 ("around 100 bits of security"); quantization level `Q = 16` — [zkGPT, Section 7.1 and Table 3](https://home.cse.ust.hk/~kaichen/papers/zkgpt-security25.pdf). Later papers describe zkGPT as a single-token, partial implementation — [DeepProve, ePrint 2026/1112](https://eprint.iacr.org/2026/1112).
- [LIT] zkGPT constraint fusion: merging adjacent rounding constraints cuts attention rounding constraints by ~30%, GeLU by ~50%, normalization by ~50%; overall 1.5x from constraint optimization (lookup time 1.8x, advice commitment 1.9x) — [zkGPT, Sections 5.3 and 7.3, Table 5](https://home.cse.ust.hk/~kaichen/papers/zkgpt-security25.pdf).
- [LIT] zkLLM: sumcheck matmul per Thaler 2013 / Ghodsi et al. 2017; BLS12-381 scalar field; Hyrax commitments; fully parallelized CUDA implementation; proofs for 13B-parameter models "under 15 minutes", under 200 kB, verified in 1–3 s — [zkLLM, arXiv 2404.16109](https://arxiv.org/html/2404.16109v1). zkGPT's table lists zkLLM on GPT-2 at 15.8 s prover on 6,912 CUDA cores, 0.54 s verifier, 126 KB — [zkGPT, Table 3](https://home.cse.ust.hk/~kaichen/papers/zkgpt-security25.pdf).
- [LIT] zkCNN: a sumcheck for FFT and convolution with linear prover time, "even faster than computing the result asymptotically"; VGG-16 in 88.3 s, 341 KB proof, 59.3 ms verifier — [zkCNN, ePrint 2021/673](https://eprint.iacr.org/2021/673).
- [LIT] DeepProve (Lagrange): "sumchecks and logup GKR", sumcheck/GKR implementation reused from scroll-tech/ceno; 12-bit quantization; README reports GPT-2 at 512 tokens in 7.6 min on a 24-core / 504 GB CPU server (1.12 tokens/s), verify 1.3 s, proof 10.7 MiB; Gemma 3 19 min — [deep-prove README](https://github.com/Lagrange-Labs/deep-prove). The paper abstract reports about 174 (GPT-2) and 86 (Gemma 3) tokens per minute, 20–60x over the state of the art, verification 1–3.7 s, and 1855 tokens/min distributed — [ePrint 2026/1112](https://eprint.iacr.org/2026/1112). The two GPT-2 throughput figures (67 vs 174 tokens/min) differ; hardware for the paper figure was not visible on the abstract page.
- [LIT] DeepProve says QKV layers "involve repeated matrix multiplications with reuse of intermediate values" and were optimized "using caching and specialized sumcheck techniques"; no numbers given — [Lagrange blog, DeepProve-1](https://lagrange.dev/blog/deepprove-1).
- [LIT] ZKTorch: compiles models into "basic blocks" proven by specialized protocols and aggregated with a parallel generalization of Mira accumulation; claims at least 3x smaller proofs than specialized protocols and up to 6x faster proving than a general-purpose zkML framework — [ZKTorch, arXiv 2507.07031](https://arxiv.org/abs/2507.07031v2).
- [LIT] Jolt Atlas paper: GPT-2 end to end ≈38 s on a MacBook Pro M3 16 GB (witness ≈7.5 s, commitment ≈3.5 s, sumcheck proving ≈16 s, reduction opening ≈7 s, HyperKZG prove ≈3 s); nanoGPT 14 s vs ezkl 237 s; no per-operator breakdown and no description of the einsum sumcheck — [Jolt Atlas, arXiv 2602.17452](https://arxiv.org/html/2602.17452v1). (That is the earlier BN254/HyperKZG build, not the current Akita one.)
- [LIT] zkAgent claims a 767x prover speedup over zkGPT on GPT-2 with a 512-token transcript — reported via search snippet of [ePrint 2026/199](https://eprint.iacr.org/2026/199); I did not read the paper.

### Inferences
- [EST] Per-element comparison (rough, different hardware and fields): zkGPT's optimized single-thread number is 0.037 s for one (32×768)·(768×3072) matmul including a 2.36M-entry weight bookkeeping table, i.e. about 15 ns per weight on a 254-bit field. jolt-atlas's fold does one `mul_i64` + one reduced add per weight on a 128-bit field, ≈5 ns per weight single-threaded by the memory-note primitive timings, before any of the improvements in Section 2. So the jolt-atlas contraction is already at or ahead of the best published per-weight cost; zkGPT's 6.5–10x was relative to a naive `2·n·m` full-multiplication memoization that jolt-atlas does not use.
- [EST] Which zkGPT fold tricks transfer: (i) *grouping* is the split-eq idea; with small-scalar multiplies it saves nothing in multiplication count but enables delayed reduction per group, which is the Section 2 proposal. (ii) *Zero skipping*: jolt-atlas pads every dimension to a power of two at compile time (CLAUDE.md behavioral contract), so 768→1024 and 3072→4096 padding means ~44% of a padded GPT-2 MLP weight matrix is zeros; the fold loops run over padded dims (`self.m/n/k` come from node dims). Iterating only the unpadded extent would save up to that fraction. `EinsumDims` is built from `ComputationNode::output_dims`, which the field's doc comment says are "padded when the model was compiled with padding" (`jolt-atlas-verifier/src/node_view.rs:22-23`), so the folds do iterate the padded extent; skipping the padding lanes would be a protocol-neutral 1.3–1.8x on fold time for non-power-of-two layers. It needs the unpadded extents passed to the layout, which the node view does not obviously expose (not checked further). (iii) *Precomputed multiples* need a `2^Q`-entry table per eq group; with i32 weights (not 16-bit) and a 128-bit field where `mul_u64` costs about two additions, it is not worth it.
- [EST] Freivalds / random projection: Thaler's protocol *is* the interactive analogue. After the verifier's random `(r_m, r_n)`, the prover works with the vectors `A(r_m,·)` and `B(·,r_n)`; no dense-matrix technique does better than touching each input once. A further projection cannot remove the fold because each weight must enter the claim.
- [EST] Structured or sparse weights: a sparse-sumcheck / sparse fold only helps if the quantized weights contain many exact zeros (pruned models) or small-magnitude entries. A cheap variant that does apply: weights quantized at scale 2^14 mostly fit in 16 bits, so the fold could use a narrower multiply (`field × u16/u32`) with more products per unreduced accumulator before reduction. That is a constant-factor refinement of the delayed-reduction proposal.
- [EST] zkCNN's FFT sumcheck is for convolutions, which jolt-atlas does not route through einsum; not applicable to the transformer workloads in the zoo.
- [EST] LogUp-GKR range checks (DeepProve, zkLLM's tlookup family) replace committed one-hot digits with a fractional-sumcheck over uncommitted data. On BN254 the owner measured it as a regression [MEMO]. On Fp128 + Akita the trade-off is different in both directions (field ops ~3–4x cheaper, commits per hot entry more expensive relative to field ops), so the earlier negative result does not transfer automatically; the note says the generic primitives were kept. Worth one re-measurement because it attacks the dominant commit stage, but it is a range-check redesign, not an einsum change.

### Gaps
- DeepProve's per-layer costs, field and PCS were not on the pages fetched; the ePrint PDF was not read. zkTorch per-block (matmul) timings were not found. Modulus "Remainder" and Polyhedra Expander were not researched within the tool-call budget; I found no reliable sources on their matmul-specific costs in this session.
- zkLLM's per-model table (prover/commit time per model size) was past the fetched portion of the page; the 713 s / 1270 s OPT-13B figures appeared only in a secondary summary and are not relied on here.
- All cross-system per-element comparisons are across different hardware, thread counts, fields, security levels and token counts; treat them as order-of-magnitude only.

## 6. Parallelism and memory inefficiencies visible in the inner loops

### Takeaway
Nothing pathological, but several constant-factor inefficiencies are visible by inspection: strided (cache-hostile) fold loops, reduced arithmetic everywhere in the fold and rounds, a heap allocation per index in the degree-2 round kernel, dense eq materialization and redundant multiplications in the batched layout, and tensor copies (`padded_pow2`, `lookup_bits`) around the fused rebase.

- [CODE] Strided fold access and per-term reduction: Section 2 (`mk_kn_mn.rs:58-66`, `k_nk_n.rs:56-64`, `abmk_abnk_abmn.rs:95-122`).
- [CODE] `sumcheck_evals` (returns `Vec<F>`) in the `EqSchedule::None` arm versus `sumcheck_evals_array::<3>` in the others: `jolt-atlas-core/src/onnx_proof/ops/einsum/dot.rs` `round_message`; array variant defined at `atlas-algebra/src/poly/multilinear_polynomial.rs:417-453`.
- [CODE] `EqPolynomial::evals` tables are materialized for `r_m`, `r_n`, `r_ab` in every fold (sizes `m`, `n`, `ab`; small): `mk_kn_mn.rs:57`, `abmk_abnk_abmn.rs:91-93`.
- [CODE] The rayon work unit in the folds is one output coefficient `j` (`into_par_iter().with_min_len(par_enabled())` over `0..k`), each doing an `m`- or `n`-long strided inner loop: same lines as above.
- [CODE] Fused rebase copies: `try_rebase_intermediates` pads both cached tensors (`padded_pow2()`); `remainder_lookup_bits` builds a `Vec<LookupBits>` per node; `deferred_lookups::prove_all` then converts indices to `Vec<u64>` and clones per bucket (`ValueProver::new(p, v.clone())`): `jolt-atlas-core/src/onnx_proof/fused_rebase.rs:139-184`, `jolt-atlas-core/src/onnx_proof/deferred_lookups.rs` remainder block.

A blocked/SIMD i64 GEMM (or i32×i32→i64 widening kernel) is a pure-engineering speedup with zero protocol risk; the memory notes say a GEMM kernel was done once on the old tracer (16 s → 3.3 s), and whether it survived the atlas-trace rewrite was not checked.

## 7. Ranked proposals
